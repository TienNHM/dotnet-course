# 10.2 - JWT Authentication

> **Tóm tắt:** Điều quan trọng nhất về JWT, và cũng bị hiểu sai nhiều nhất: **JWT được ký, không được mã hoá**. Payload chỉ là Base64Url — **bất kỳ ai cầm token đều đọc được** toàn bộ nội dung, không cần khoá. Chữ ký chỉ đảm bảo token **không bị sửa**. Nên đừng bao giờ đặt thông tin nhạy cảm vào payload. Hai quyết định cấu hình quan trọng: **`ClockSkew`** mặc định là **5 phút**, nghĩa là token đã hết hạn vẫn được chấp nhận thêm 5 phút nữa; và **khoá ký phải dài hơn 256 bit** cho HMAC-SHA256, nếu không thư viện từ chối ký. Và giới hạn cốt lõi của JWT: nó **không thu hồi được** — token đã phát ra sẽ hợp lệ tới khi hết hạn, bất kể bạn làm gì.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích ba phần của JWT và ý nghĩa từng claim chuẩn.
- Dựng endpoint đăng nhập phát JWT và bảo vệ API bằng `[Authorize]`.
- Cấu hình `TokenValidationParameters` an toàn và biết tham số nào thật sự kiểm chữ ký.
- Chọn giữa HMAC và RSA để ký token.
- Giải thích vì sao JWT không thu hồi được và cách sống chung với điều đó.

**Cần biết trước:** [bài 10.1](10.1-authentication-vs-authorization.md) (401/403, claim), hệ thống cấu hình và user-secrets ([bài 8.6](../module-08-aspnet-core-fundamentals/8.6-configuration-system.md)), Options pattern ([bài 7.7](../../stage-02-csharp-professional/module-07-dependency-injection/7.7-options-pattern.md)). Bài tập 3 dùng `WebApplicationFactory` của [bài 9.8](../module-09-web-api-professional/9.8-api-testing.md).

## Nội dung bài học

### 10.2.1 — Cấu trúc và những gì nó không làm

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9      <- Header
.eyJzdWIiOiIxMjMiLCJyb2xlIjoiU2FsZXNSZXAifQ <- Payload
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c <- Signature
```

Ba phần, hai phần đầu là **Base64Url của JSON** — không mã hoá, chỉ đổi cách biểu diễn ký tự. Dán bất kỳ token nào vào một trang giải mã Base64 và bạn đọc được toàn bộ payload.

```json
{
  "sub": "8f14e45f-ceea-467a-9f36-6c2e0b1b6d3a",
  "email": "a.nguyen@crm.com",
  "role": "SalesRep",
  "iss": "crm-api",
  "aud": "crm-client",
  "exp": 1792292162,
  "iat": 1792291262,
  "jti": "d5614f62-ab56-4cb1-ba60-4c3f836056e2"
}
```

| Claim | Nghĩa | Bắt buộc? |
|---|---|---|
| `sub` | Chủ thể — id người dùng | Có |
| `iss` | Ai phát hành token | Có |
| `aud` | Token dành cho ai dùng | Có |
| `exp` | Hết hạn lúc nào (Unix seconds) | Có |
| `iat` | Phát hành lúc nào | Nên có |
| `jti` | Id duy nhất của token | Nên có — để blacklist |

`aud` quan trọng hơn vẻ ngoài: nó ngăn token phát cho service A được dùng ở service B. Không kiểm tra `aud`, một token hợp lệ cho ứng dụng nội bộ có thể dùng được trên API công khai.

**Hệ quả của "chỉ ký, không mã hoá":**

```csharp
// SAI — ai cầm token cũng đọc được
claims.Add(new Claim("salary", "50000000"));
claims.Add(new Claim("ssn", "001234567890"));
claims.Add(new Claim("internal_notes", "..."));
```

Cần bí mật thật thì dùng JWE (JSON Web Encryption), hoặc đơn giản hơn: **đừng đặt nó vào token**.

### 10.2.2 — Chuẩn bị project

Bài này dùng project Web API có controller như [bài 8.4](../module-08-aspnet-core-fundamentals/8.4-controllers-and-actions.md). Thêm gói xác thực JWT và tạo khoá ký:

```bash
dotnet add package Microsoft.AspNetCore.Authentication.JwtBearer
dotnet user-secrets init
dotnet user-secrets set "Jwt:SecretKey" "$(openssl rand -base64 48)"
```

`openssl rand -base64 48` sinh 48 byte ngẫu nhiên (384 bit). Khoá là **secret**, nên nó nằm trong user-secrets khi phát triển và trong biến môi trường hoặc Key Vault khi chạy thật, không bao giờ nằm trong `appsettings.json` ([bài 8.6](../module-08-aspnet-core-fundamentals/8.6-configuration-system.md)). Phần không bí mật thì để trong `appsettings.json`:

```json
{
  "Jwt": {
    "Issuer": "crm-api",
    "Audience": "crm-client",
    "AccessTokenMinutes": 15
  }
}
```

```csharp
// JwtOptions.cs
public sealed class JwtOptions
{
    public string Issuer { get; set; } = "";
    public string Audience { get; set; } = "";
    public string SecretKey { get; set; } = "";
    public int AccessTokenMinutes { get; set; } = 15;
}
```

```csharp
// Program.cs
builder.Services.AddOptions<JwtOptions>()
    .Bind(builder.Configuration.GetSection("Jwt"))
    .Validate(o => Encoding.UTF8.GetByteCount(o.SecretKey) >= 32,
              "Jwt:SecretKey phải tối thiểu 32 byte")
    .ValidateOnStart();
```

Quên chạy lệnh `user-secrets set` thì ứng dụng dừng ngay lúc khởi động, thay vì chạy với khoá rỗng:

```text
Microsoft.Extensions.Options.OptionsValidationException: Jwt:SecretKey phải tối thiểu 32 byte
```

### 10.2.3 — Cấu hình xác thực

```csharp
// Program.cs
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        var jwt = builder.Configuration.GetSection("Jwt").Get<JwtOptions>()!;

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer   = true,
            ValidIssuer      = jwt.Issuer,

            ValidateAudience = true,
            ValidAudience    = jwt.Audience,

            IssuerSigningKey = new SymmetricSecurityKey(
                                   Encoding.UTF8.GetBytes(jwt.SecretKey)),

            ValidateLifetime = true,
            ClockSkew        = TimeSpan.FromSeconds(30),

            ValidAlgorithms  = [SecurityAlgorithms.HmacSha256],   // chốt thuật toán
        };
        // MapInboundClaims giữ mặc định (true): đọc claim bằng ClaimTypes.*, xem bài 10.1
    });

builder.Services.AddAuthorization();
```

```csharp
// Program.cs, phần pipeline
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
```

**Những tham số không được tắt, và chuyện gì xảy ra nếu tắt:**

| Tham số | Mặc định | Đặt sai thì |
|---|---|---|
| `RequireSignedTokens` | `true` | `false`: token **không có chữ ký** (header `"alg": "none"`) được chấp nhận. Chạy thử: token tự chế vai trò `Admin` gọi được endpoint Admin |
| `IssuerSigningKey` | không có | Phải là khoá của chính bạn. Đặt nhầm một khoá ai cũng biết là ai cũng tự ký được token |
| `ValidateLifetime` | `true` | Token không bao giờ hết hạn |
| `ValidateIssuer` | `true` | Token của hệ thống khác dùng được ở đây |
| `ValidateAudience` | `true` | Token cho service khác dùng được ở đây |

**`ValidateIssuerSigningKey` không phải công tắc kiểm chữ ký.** Tên của nó gây hiểu nhầm rất phổ biến. Nó chỉ bật thêm bước kiểm tra **bản thân khoá** (ví dụ chứng chỉ X.509 còn hạn không), mặc định là `false`, và chữ ký vẫn luôn được kiểm khi có `IssuerSigningKey`. Chạy thử trên .NET 10 với `ValidateIssuerSigningKey = false`: token ký bằng khoá khác vẫn bị từ chối với `error_description="The signature key was not found"`. Thứ thật sự tắt được việc kiểm chữ ký là `RequireSignedTokens = false` hoặc tự gán một `SignatureValidator` không kiểm gì — cả hai đều không bao giờ nên xuất hiện trong code production.

Người ta hay đổi các tham số này "tạm thời để debug" rồi quên đổi lại. Bài tập 3 viết test chặn chuyện đó.

`ValidAlgorithms` là tầng phòng thủ đáng thêm: nó chốt cứng thuật toán, ngăn thuộc tính `alg` trong header token quyết định cách xác thực.

### 10.2.4 — `ClockSkew`: mặc định 5 phút

Mặc định của `TokenValidationParameters` là **`ClockSkew = 5 phút`** — token đã hết hạn vẫn được chấp nhận thêm 5 phút nữa, để bù cho đồng hồ lệch giữa các máy.

Với access token 15 phút, nghĩa là thời gian sống thật là **20 phút** — tăng 33%. Đó là điều bạn phải biết khi thiết kế, không phải phát hiện lúc điều tra sự cố.

```csharp
ClockSkew = TimeSpan.Zero;               // chính xác tuyệt đối
ClockSkew = TimeSpan.FromSeconds(30);    // đủ cho NTP lệch bình thường
```

`Zero` nghe an toàn nhất nhưng gây lỗi giả khi đồng hồ server lệch vài giây — và trong môi trường container, lệch vài giây là bình thường. **30 giây** là con số cân bằng.

Nếu bạn dùng `Zero`, hãy chắc chắn mọi máy đều đồng bộ NTP (Network Time Protocol, giao thức đồng bộ đồng hồ qua mạng).

### 10.2.5 — HMAC hay RSA

```csharp
// HMAC (HS256) — MỘT khoá bí mật dùng chung
var hmacKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secret));
var hmacCredentials = new SigningCredentials(hmacKey, SecurityAlgorithms.HmacSha256);

// RSA (RS256) — khoá RIÊNG để ký, khoá CÔNG để xác thực
var rsa = RSA.Create();
rsa.ImportFromPem(privateKeyPem);
var rsaCredentials = new SigningCredentials(new RsaSecurityKey(rsa), SecurityAlgorithms.RsaSha256);
```

| | HMAC (HS256) | RSA (RS256) |
|---|---|---|
| Khoá | Một, dùng chung | Cặp riêng/công |
| Ai xác thực được | Ai có khoá bí mật | Ai có khoá công |
| Ai **phát hành** được | **Ai có khoá bí mật** | Chỉ người có khoá riêng |
| Tốc độ | Nhanh hơn | Chậm hơn |
| Hợp với | Một service tự phát và tự xác thực | Nhiều service, identity provider riêng |

Điểm quyết định nằm ở dòng thứ ba. Với HMAC, **mọi service xác thực được token cũng phát hành được token**. Chia sẻ khoá HMAC cho 5 microservice nghĩa là bất kỳ service nào bị xâm nhập cũng có thể tự phát token admin.

Với RSA, service chỉ cần khoá **công** để xác thực — nó không thể giả mạo token.

Quy tắc: **một ứng dụng tự phát và tự xác thực thì HMAC đủ. Từ hai service trở lên thì RSA.** Và khi dùng identity provider (Microsoft Entra ID, Auth0, Keycloak) thì bạn luôn dùng thuật toán bất đối xứng với khoá công lấy từ endpoint JWKS (danh sách khoá công khai mà provider công bố).

**Khoá HMAC phải dài hơn 256 bit** cho HS256. Thư viện từ chối ngay lúc ký nếu khoá ngắn, ví dụ với khoá 16 byte:

```text
IDX10720: Unable to create KeyedHashAlgorithm for algorithm 'HS256',
the key size must be greater than: '256' bits, key has '128' bits.
```

Vì vậy hãy sinh khoá bằng `openssl rand -base64 48` như mục 10.2.2, đừng gõ tay.

### 10.2.6 — Phát hành token

Từ .NET 8, JwtBearer dùng `JsonWebTokenHandler` (gói `Microsoft.IdentityModel.JsonWebTokens`, có sẵn khi bạn cài JwtBearer). Phát token bằng cùng thư viện đó:

```csharp
// TokenService.cs
public sealed class TokenService(IOptions<JwtOptions> options, TimeProvider clock)
{
    private readonly JwtOptions _jwt = options.Value;
    private readonly JsonWebTokenHandler _handler = new();

    public string CreateAccessToken(string userId, string email, IEnumerable<string> roles)
    {
        var now = clock.GetUtcNow().UtcDateTime;

        var claims = new List<Claim>
        {
            new(JwtRegisteredClaimNames.Sub, userId),
            new(JwtRegisteredClaimNames.Email, email),
            new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
        };
        claims.AddRange(roles.Select(r => new Claim("role", r)));

        var descriptor = new SecurityTokenDescriptor
        {
            Issuer = _jwt.Issuer,
            Audience = _jwt.Audience,
            Subject = new ClaimsIdentity(claims),
            IssuedAt = now,
            NotBefore = now,
            Expires = now.AddMinutes(_jwt.AccessTokenMinutes),
            SigningCredentials = new SigningCredentials(
                new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_jwt.SecretKey)),
                SecurityAlgorithms.HmacSha256),
        };

        return _handler.CreateToken(descriptor);
    }
}
```

```csharp
// Program.cs
builder.Services.AddSingleton(TimeProvider.System);
builder.Services.AddSingleton<TokenService>();
```

Token ghi tên claim ngắn (`sub`, `email`, `role`). Khi đọc lại, handler đổi chúng thành `ClaimTypes.NameIdentifier`, `ClaimTypes.Email`, `ClaimTypes.Role` như đã nói ở [bài 10.1](10.1-authentication-vs-authorization.md). Payload thật của một token do service này phát cho Admin:

```json
{"aud":"crm-client","iss":"crm-api","exp":1792292162,"iat":1792291262,"nbf":1792291262,"sub":"3","email":"admin@crm.local","jti":"d5614f62-ab56-4cb1-ba60-4c3f836056e2","role":"Admin"}
```

Tiêm `TimeProvider` thay vì gọi `DateTime.UtcNow` để test được hành vi hết hạn — [bài 7.1](../../stage-02-csharp-professional/module-07-dependency-injection/7.1-di-problem-scope.md).

`jti` cho phép blacklist một token cụ thể; `iat` giúp phát hiện token quá cũ ngay cả khi `exp` còn hạn.

Nhiều tài liệu cũ dùng `JwtSecurityToken` và `JwtSecurityTokenHandler` (gói `System.IdentityModel.Tokens.Jwt`). Chúng vẫn chạy, nhưng Microsoft khuyên dùng `JsonWebTokenHandler` cho code mới vì nhanh hơn và là thứ JwtBearer dùng bên trong.

### 10.2.7 — Endpoint đăng nhập

Bài này chưa dùng database người dùng. ASP.NET Core Identity, thư viện quản lý người dùng đầy đủ, được dạy ở [bài 10.8](10.8-overview.md). Tạm thời dùng một kho người dùng trong bộ nhớ, mật khẩu vẫn được băm bằng `PasswordHasher` của Identity chứ không lưu thô:

```csharp
// DemoUserStore.cs
public sealed record DemoUser(string Id, string Email, string PasswordHash, string[] Roles);

public sealed class DemoUserStore
{
    private readonly List<DemoUser> _users = [];
    private readonly PasswordHasher<DemoUser> _hasher = new();

    public DemoUserStore()
    {
        Add("1", "an@crm.local", "Mat-khau-cua-An-2026", ["SalesRep"]);
        Add("2", "binh@crm.local", "Mat-khau-cua-Binh-2026", ["Manager"]);
        Add("3", "admin@crm.local", "Mat-khau-cua-Admin-2026", ["Admin"]);
    }

    private void Add(string id, string email, string password, string[] roles)
    {
        var user = new DemoUser(id, email, "", roles);
        _users.Add(user with { PasswordHash = _hasher.HashPassword(user, password) });
    }

    public DemoUser? FindByEmail(string email) =>
        _users.FirstOrDefault(u => u.Email.Equals(email, StringComparison.OrdinalIgnoreCase));

    public DemoUser? FindById(string id) => _users.FirstOrDefault(u => u.Id == id);

    public bool CheckPassword(DemoUser user, string password) =>
        _hasher.VerifyHashedPassword(user, user.PasswordHash, password)
            != PasswordVerificationResult.Failed;
}
```

```csharp
// AuthController.cs
public sealed record LoginRequest(string Email, string Password);
public sealed record TokenResponse(string AccessToken, int ExpiresIn);

[ApiController]
[Route("api/auth")]
public sealed class AuthController(
    DemoUserStore users, TokenService tokens, IOptions<JwtOptions> jwt,
    ILogger<AuthController> logger) : ControllerBase
{
    [HttpPost("login")]
    [AllowAnonymous]
    [EnableRateLimiting("login")]              // chống dò mật khẩu, xem Program.cs bên dưới
    public ActionResult<TokenResponse> Login(LoginRequest request)
    {
        var user = users.FindByEmail(request.Email);

        // Thông báo GIỐNG NHAU cho mọi trường hợp thất bại
        if (user is null || !users.CheckPassword(user, request.Password))
        {
            logger.LogWarning("Đăng nhập thất bại cho {Email} từ {Ip}",
                request.Email, HttpContext.Connection.RemoteIpAddress);

            return Unauthorized(new ProblemDetails
            {
                Title = "Đăng nhập thất bại",
                Detail = "Email hoặc mật khẩu không đúng.",
            });
        }

        var accessToken = tokens.CreateAccessToken(user.Id, user.Email, user.Roles);
        return Ok(new TokenResponse(accessToken, jwt.Value.AccessTokenMinutes * 60));
    }
}
```

```csharp
// Program.cs
builder.Services.AddSingleton<DemoUserStore>();
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.AddPolicy("login", context => RateLimitPartition.GetFixedWindowLimiter(
        context.Connection.RemoteIpAddress?.ToString() ?? "unknown",
        _ => new FixedWindowRateLimiterOptions { PermitLimit = 5, Window = TimeSpan.FromMinutes(1) }));
});

// ... sau builder.Build()
app.UseRateLimiter();
```

Bảy lần đăng nhập sai liên tiếp từ cùng một IP cho ra (chạy thật):

```text
401 401 401 401 401 429 429
```

Ba điểm bảo mật trong đoạn ngắn này:

**1. Thông báo lỗi giống nhau.** "Email không tồn tại" và "Mật khẩu sai" cho kẻ tấn công biết email nào có trong hệ thống — đó là bước đầu của tấn công dò tài khoản.

**2. Rate limit là bắt buộc.** Không có nó, endpoint đăng nhập là cửa mở cho dò mật khẩu tự động ([bài 9.6](../module-09-web-api-professional/9.6-rate-limiting.md)). Khoá tài khoản sau nhiều lần sai (lockout) là tầng thứ hai, có sẵn trong Identity ở [bài 10.8](10.8-overview.md).

**3. Log mọi lần thất bại** kèm IP. Đây là nguồn dữ liệu duy nhất để phát hiện tấn công đang diễn ra.

Một điểm tinh tế: khi không tìm thấy user, code trả lời **nhanh hơn** hẳn so với khi phải chạy hàm băm mật khẩu, nên thời gian phản hồi tiết lộ email có tồn tại hay không. Với hệ thống cần chống điều này, hãy băm một mật khẩu giả khi không tìm thấy user.

<small>File gốc: [nền sáng](../../../diagrams/stage-03-aspnet-core-backend/module-10-authentication-authorization/jwt-issue-validate.html) · [nền tối](../../../diagrams/stage-03-aspnet-core-backend/module-10-authentication-authorization/jwt-issue-validate-dark.html)</small>

Refresh token, thứ giúp người dùng không phải đăng nhập lại mỗi 15 phút, được thêm vào endpoint này ở [bài 10.3](10.3-refresh-token.md).

### 10.2.8 — JWT không thu hồi được

Đây là đánh đổi cốt lõi của JWT, và phải hiểu rõ trước khi chọn nó.

Server **không lưu** gì về token. Nó chỉ xác thực chữ ký và hạn. Hệ quả: **token đã phát ra hợp lệ cho tới khi hết hạn**, kể cả khi người dùng đã đăng xuất, bị khoá tài khoản, hay bị thu hồi quyền. Khởi động lại ứng dụng cũng không làm token cũ mất hiệu lực, vì khoá ký nằm trong cấu hình chứ không nằm trong bộ nhớ tiến trình.

| Muốn | Với session | Với JWT |
|---|---|---|
| Đăng xuất ngay lập tức | Xoá session | **Không làm được** |
| Khoá tài khoản ngay | Xoá session | **Không làm được** |
| Thu hồi quyền ngay | Cập nhật session | **Không làm được** |
| Scale ngang không cần kho chung | Cần Redis | **Làm được** |

Ba cách sống chung:

1. **TTL ngắn** — 5 đến 15 phút. Đơn giản nhất và đủ cho phần lớn hệ thống: cửa sổ rủi ro là 15 phút.
2. **Blacklist theo `jti`** trong Redis với TTL bằng hạn còn lại của token. Nó **phá** tính stateless, nhưng kho này nhỏ và tra cứu nhanh.
3. **`SecurityStamp`** — mỗi lần đổi mật khẩu hay thu hồi quyền thì đổi stamp, và token mang stamp cũ bị từ chối. Cần tra database mỗi request, nên thường dùng kèm cache ngắn ([bài 10.8](10.8-overview.md)).

Nếu bạn cần đăng xuất **ngay lập tức** và hệ thống chỉ có một service, session truyền thống có thể là lựa chọn đúng hơn JWT. JWT không phải luôn tốt hơn — nó đánh đổi khả năng thu hồi lấy khả năng scale.

### 10.2.9 — Lỗi thường gặp

**Danh sách rà soát JWT**

- [ ] Không có thông tin nhạy cảm nào trong payload — nó đọc được công khai.
- [ ] RequireSignedTokens, ValidateLifetime, ValidateIssuer, ValidateAudience giữ giá trị true.
- [ ] Không có SignatureValidator tự viết nào bỏ qua việc kiểm chữ ký.
- [ ] ValidAlgorithms được khai rõ, không để thuật toán do token quyết định.
- [ ] ClockSkew được đặt có chủ đích, biết rõ mặc định là 5 phút.
- [ ] Khoá ký dài hơn 256 bit, sinh ngẫu nhiên, nằm trong user-secrets, biến môi trường hoặc Key Vault.
- [ ] Nhiều service thì dùng RSA, không chia sẻ khoá HMAC.
- [ ] Access token có TTL ngắn, từ 5 đến 15 phút.
- [ ] Token có jti để blacklist được khi cần.
- [ ] Endpoint đăng nhập có rate limit.
- [ ] Thông báo lỗi đăng nhập giống nhau cho mọi nguyên nhân thất bại.
- [ ] Có test kiểm tra token ký bằng khoá sai và token không chữ ký đều bị từ chối.

## Bài tập áp dụng

#### Bài 1 — Đọc payload của chính token mình phát

Lấy một token do hệ thống bạn phát, tách phần giữa và giải mã Base64Url. Liệt kê những gì lộ ra và đánh giá có gì không nên ở đó.

**Tiêu chí hoàn thành:** bạn giải mã được **mà không cần khoá bí mật**, và nêu được điều đó nói gì về những thứ được phép đặt trong token.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** JWT có ba phần ngăn bởi dấu chấm. Phần giữa chỉ được **mã hoá Base64Url**, không phải **mã hoá bí mật**. Hai việc đó khác nhau hoàn toàn.

**Lời giải — giải mã bằng một dòng:**

```bash
echo "$TOKEN" | cut -d. -f2 | base64 -d 2>/dev/null | jq .
```

Base64Url bỏ dấu `=` ở cuối nên đôi khi cần đệm lại:

```bash
python3 -c "
import base64,json,sys
p = sys.argv[1].split('.')[1]
p += '=' * (-len(p) % 4)
print(json.dumps(json.loads(base64.urlsafe_b64decode(p)), indent=2, ensure_ascii=False))
" "$TOKEN"
```

**Một payload có vấn đề** (ví dụ minh hoạ, không phải token do code trong bài phát):

```json
{
  "sub": "8f3a1b2c-0000-0000-0000-000000000001",
  "email": "an@company.com",
  "name": "Nguyễn Văn An",
  "role": ["Manager", "SalesRep"],
  "tenant_id": "acme",
  "salary_band": "B3",
  "internal_note": "đang trong diện xem xét kỷ luật",
  "exp": 1790000000,
  "iat": 1789999100,
  "iss": "crm-api",
  "aud": "crm-client"
}
```

**Không cần khoá bí mật nào.** Đây là điểm mấu chốt: chữ ký bảo vệ **tính toàn vẹn** (không ai sửa được nội dung mà không bị phát hiện), chứ không bảo vệ **tính bí mật**. Bất kỳ ai cầm token — kể cả JavaScript trên trình duyệt, kể cả một log file, kể cả người ngồi cạnh nhìn màn hình — đều đọc được toàn bộ payload.

**Hai trường trong ví dụ trên không nên có ở đó:**

| Trường | Vấn đề |
|---|---|
| `salary_band` | Dữ liệu nhân sự nhạy cảm, lộ cho bất kỳ ai xem được token |
| `internal_note` | Ghi chú nội bộ — người dùng đọc được chính ghi chú về mình |

**Quy tắc đặt claim, theo ba câu hỏi:**

1. *Người dùng đọc được nó có sao không?* Không sao thì mới được đặt.
2. *Nó có cần cho mọi request không?* Không thì để ở endpoint riêng, đừng mang theo mãi.
3. *Nó có đổi trong vòng đời token không?* Có thì đừng đặt — token không cập nhật được.

**Điều này cũng giải thích vì sao đừng bao giờ ghi token vào log.** Một dòng log tưởng vô hại:

```csharp
_logger.LogDebug("Gọi API với token {Token}", token);   // SAI
```

Người đọc được log giờ đọc được mọi claim của mọi người dùng, và dùng lại token đó cho tới khi hết hạn. Cấu hình che header `Authorization` là bắt buộc, như [bài 8.7](../module-08-aspnet-core-fundamentals/8.7-logging-with-serilog.md) trình bày.

**Nếu thật sự cần giấu nội dung**, JWT có bản mã hoá là **JWE** — nhưng gần như không đáng dùng cho API nội bộ. Cách đơn giản hơn nhiều: chỉ đặt một `sub` trong token và tra mọi thứ khác từ database.

</details>

#### Bài 2 — `ClockSkew` mặc định kéo dài tuổi token thêm 5 phút

Bỏ dòng `ClockSkew` khỏi cấu hình (tức dùng mặc định), rồi gọi API bằng một token **đã hết hạn 2 phút**. Xác nhận nó **vẫn được chấp nhận**. Đặt `ClockSkew = TimeSpan.Zero` và kiểm chứng lại.

**Tiêu chí hoàn thành:** bạn tính được **tuổi thọ thật** của access token trong hệ thống mình, và nêu được vì sao `Zero` không phải lựa chọn mặc định tốt.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** `exp` trong token không phải thời điểm token ngừng được chấp nhận. Thời điểm đó là `exp + ClockSkew`.

**Lời giải — tạo token đã hết hạn**, khỏi phải ngồi chờ:

```csharp
var now = DateTime.UtcNow;
var expiredToken = new JsonWebTokenHandler().CreateToken(new SecurityTokenDescriptor
{
    Issuer = "crm-api",
    Audience = "crm-client",
    Subject = new ClaimsIdentity([new Claim("sub", "42")]),
    NotBefore = now.AddMinutes(-3),
    IssuedAt = now.AddMinutes(-3),
    Expires = now.AddMinutes(-2),                       // đã hết hạn 2 phút
    SigningCredentials = new SigningCredentials(
        new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey)),
        SecurityAlgorithms.HmacSha256),
});
```

**Kết quả chạy thật**, gọi `GET /api/v1/customers` (có `[Authorize]`):

```text
ClockSkew mặc định (5 phút):  200
ClockSkew = TimeSpan.Zero:    401
```

```http
WWW-Authenticate: Bearer error="invalid_token", error_description="The token expired at '10/18/2026 02:39:03'"
```

**Vẫn 200 dù token đã hết hạn 2 phút.**

**Tuổi thọ thật của token:**

| Cấu hình | `exp` đặt | Thật sự dùng được | Chênh |
|---|---|---|---|
| Mặc định | 15 phút | **20 phút** | **+33%** |
| `FromSeconds(30)` | 15 phút | 15,5 phút | +3% |
| `Zero` | 15 phút | 15 phút | 0% |

Con số này quan trọng khi bạn thiết kế thời hạn. Chọn 5 phút cho access token mà không biết về `ClockSkew` thì thật ra bạn đang chạy với 10 phút — gấp đôi ý định.

**Vì sao `Zero` không phải mặc định tốt.** Nó bắt đồng hồ của máy phát token và máy kiểm token khớp nhau tới từng giây. Trong container, lệch vài giây là chuyện bình thường, và hậu quả là **lỗi 401 ngẫu nhiên** cho token vừa được cấp — kiểu lỗi không tái hiện được, không có trong log ứng dụng, và rất tốn thời gian điều tra. Ca ở [bài 2.11](../../stage-01-foundation/module-02-computer-science-basics/2.11-mini-case-study.md) là đúng tình huống này, chỉ khác chiều lệch.

**`30 giây` là con số cân bằng:** đủ bù cho lệch NTP bình thường, và chỉ kéo dài tuổi token thêm 3%.

**Nếu bạn chọn `Zero`, phải kèm hai thứ:** máy chủ bật đồng bộ thời gian (trên Linux: `timedatectl set-ntp true`, rồi `timedatectl status` thấy `System clock synchronized: yes`), và một health check theo dõi độ lệch đồng hồ, để lần sau hệ thống tự báo thay vì chờ người dùng phát hiện.

**Một chi tiết ít người biết:** `ClockSkew` áp cho **cả `nbf`** (not before), không chỉ `exp`. Token phát ra với `nbf` trong tương lai gần vẫn được chấp nhận sớm — điều này quan trọng nếu bạn dùng `nbf` để lên lịch hiệu lực.

</details>

#### Bài 3 — Bài test chứng minh chữ ký thật sự được kiểm

Viết hai integration test: token ký bằng khoá khác phải nhận `401`, token không có chữ ký phải nhận `401`. Sau đó lần lượt đổi `ValidateIssuerSigningKey = false` và `RequireSignedTokens = false`, chạy lại và ghi lại test nào đỏ.

**Tiêu chí hoàn thành:** bạn chỉ ra được tham số nào thật sự canh việc kiểm chữ ký, và giải thích vì sao bước "đổi cấu hình rồi xem test đỏ" là phần **quan trọng nhất** của bài.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Một bài test luôn xanh không chứng minh được gì — kể cả khi nó xanh vì lý do sai.

**Lời giải — hai bài test** (cần project test xUnit tham chiếu project API và gói `Microsoft.AspNetCore.Mvc.Testing`, như [bài 9.8](../module-09-web-api-professional/9.8-api-testing.md); `Program.cs` của API cần dòng `public partial class Program;` ở cuối):

```csharp
// TokenValidationTests.cs
public class TokenValidationTests
{
    private readonly WebApplicationFactory<Program> _factory = new WebApplicationFactory<Program>()
        .WithWebHostBuilder(b =>
            b.UseSetting("Jwt:SecretKey", "khoa-bi-mat-cho-test-du-dai-32-byte-tro-len!!"));

    private static string CreateToken(SigningCredentials? credentials)
    {
        var descriptor = new SecurityTokenDescriptor
        {
            Issuer = "crm-api",
            Audience = "crm-client",
            Subject = new ClaimsIdentity([new Claim("sub", "42"), new Claim("role", "Admin")]),
            Expires = DateTime.UtcNow.AddMinutes(15),
            SigningCredentials = credentials,
        };
        return new JsonWebTokenHandler().CreateToken(descriptor);
    }

    private async Task<HttpStatusCode> CallAdminAsync(string token)
    {
        var client = _factory.CreateClient();
        client.DefaultRequestHeaders.Authorization = new("Bearer", token);
        var res = await client.GetAsync("/api/v1/admin/users");
        return res.StatusCode;
    }

    [Fact]
    public async Task TokenSignedWithWrongKey_Returns401()
    {
        var attackerKey = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes("khoa-cua-ke-tan-cong-du-dai-32-byte!!"));
        var token = CreateToken(new SigningCredentials(attackerKey, SecurityAlgorithms.HmacSha256));

        Assert.Equal(HttpStatusCode.Unauthorized, await CallAdminAsync(token));
    }

    [Fact]
    public async Task UnsignedToken_Returns401()
    {
        var token = CreateToken(credentials: null);     // header "alg": "none", không có chữ ký

        Assert.Equal(HttpStatusCode.Unauthorized, await CallAdminAsync(token));
    }
}
```

Chạy — **cả hai xanh**.

**Đổi lần 1: `ValidateIssuerSigningKey = false`.** Chạy lại:

```text
Passed!  - Failed:     0, Passed:     2, Skipped:     0, Total:     2
```

**Vẫn xanh cả hai.** Đây là kết quả quan trọng: tham số mang tên "validate signing key" **không** phải công tắc kiểm chữ ký. Nếu bạn tin vào cái tên và dựa vào nó để "tắt tạm" khi debug, bạn đã hiểu sai cấu hình của chính mình — và chỉ một bài test mới cho bạn thấy điều đó.

**Đổi lần 2: `RequireSignedTokens = false`.** Chạy lại:

```text
Failed JwtLab.Tests.TokenValidationTests.UnsignedToken_Returns401
  Error Message:
   Assert.Equal() Failure: Values differ
Expected: Unauthorized
Actual:   OK
```

**Test đỏ.** Token không chữ ký, tự khai vai trò `Admin`, gọi được endpoint chỉ dành cho Admin. Đây là van thật sự.

**Vì sao bước này quan trọng nhất.** Bài test đầu tiên xanh, nhưng bạn chưa biết nó xanh vì **lý do gì**. Nó có thể xanh vì:

- chữ ký bị từ chối — điều bạn muốn kiểm,
- hoặc `issuer` sai,
- hoặc `audience` sai,
- hoặc token hết hạn,
- hoặc endpoint đó vốn đã `401` cho mọi thứ vì cấu hình sai chỗ khác.

Cả năm khả năng đều cho `401`. Chỉ khi **tắt đúng cái van bạn đang kiểm** và thấy test chuyển sang đỏ, bạn mới biết test đang canh đúng thứ. Đây là ý tưởng của kiểm thử đột biến (mutation testing: cố ý làm hỏng code để xem test có phát hiện không), áp dụng bằng tay cho một trường hợp. Lần đổi thứ nhất cho thấy mặt còn lại: đổi nhầm van thì test vẫn xanh, và bạn học được điều gì đó về cấu hình chứ không phải về test.

**Vì sao token không chữ ký là thảm hoạ.** Bất kỳ ai cũng tự viết được payload `{"sub":"1","role":"Admin",...}`, mã hoá Base64Url và gửi đi. Không cần khoá, không cần công cụ đặc biệt.

**Mỗi van một bài test:**

| Tham số | Bài test canh nó |
|---|---|
| `RequireSignedTokens` | Token không chữ ký bị `401` |
| `IssuerSigningKey` | Token ký bằng khoá khác bị `401` |
| `ValidateIssuer` | Token có `iss` lạ bị `401` |
| `ValidateAudience` | Token có `aud` của service khác bị `401` |
| `ValidateLifetime` | Token đã hết hạn quá `ClockSkew` bị `401` |

Viết đủ năm bài test theo đúng khuôn trên. Chúng rẻ, chạy trong vài trăm mili-giây, và chặn được loại lỗi mà không ai phát hiện khi review — vì cấu hình sai **vẫn chạy đúng** với mọi token hợp lệ.

</details>

## Tự kiểm tra

<details>
<summary>JWT có mã hoá nội dung không?</summary>

Không, nó chỉ được ký. Payload là Base64Url của JSON nên bất kỳ ai cầm token đều đọc được toàn bộ nội dung mà không cần khoá. Chữ ký chỉ đảm bảo token không bị sửa. Vì vậy không bao giờ đặt thông tin nhạy cảm vào payload.

</details>

<details>
<summary>Tham số nào thật sự quyết định token không chữ ký có bị từ chối không?</summary>

RequireSignedTokens, mặc định là true. Đặt false thì token có header alg none được chấp nhận. ValidateIssuerSigningKey thì khác: nó chỉ kiểm tra bản thân khoá, mặc định là false, và đặt false không làm chữ ký ngừng được kiểm. Cùng với đó phải giữ ValidateLifetime, ValidateIssuer và ValidateAudience là true.

</details>

<details>
<summary>ClockSkew mặc định là bao nhiêu và vì sao quan trọng?</summary>

Năm phút. Nghĩa là token đã hết hạn vẫn được chấp nhận thêm 5 phút nữa, nên access token 15 phút có thời gian sống thật là 20 phút. Đặt về 0 thì chính xác nhưng gây lỗi giả khi đồng hồ lệch vài giây, điều rất bình thường trong container; 30 giây là con số cân bằng.

</details>

<details>
<summary>Khi nào phải dùng RSA thay vì HMAC?</summary>

Khi có từ hai service trở lên. Với HMAC, mọi service xác thực được token cũng phát hành được token, nên chia sẻ khoá cho 5 microservice nghĩa là bất kỳ service nào bị xâm nhập cũng tự phát được token admin. Với RSA, service chỉ cần khoá công để xác thực và không thể giả mạo.

</details>

<details>
<summary>Vì sao thông báo lỗi đăng nhập phải giống nhau?</summary>

Vì phân biệt email không tồn tại với mật khẩu sai cho kẻ tấn công biết email nào có trong hệ thống, đó là bước đầu của tấn công dò tài khoản. Cần chú ý cả thời gian phản hồi, vì tìm không thấy user thường nhanh hơn kiểm tra mật khẩu.

</details>

<details>
<summary>Vì sao JWT không thu hồi được và làm sao sống chung?</summary>

Vì server không lưu gì về token, chỉ xác thực chữ ký và hạn, nên token đã phát ra hợp lệ tới khi hết hạn kể cả khi người dùng đã đăng xuất hay bị khoá. Ba cách sống chung: TTL ngắn từ 5 tới 15 phút, blacklist theo jti trong Redis, hoặc dùng SecurityStamp đổi mỗi lần thu hồi quyền.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **JWT được ký, không mã hoá.** Payload là công khai với bất kỳ ai cầm token.
2. **Biết đúng van nào canh chữ ký.** `RequireSignedTokens` và khoá ký của bạn, không phải `ValidateIssuerSigningKey`; và chỉ test đổi-cấu-hình-thấy-đỏ mới chứng minh được điều đó.
3. **JWT đánh đổi khả năng thu hồi lấy khả năng scale.** TTL ngắn, `ClockSkew` 30 giây là cách sống chung đơn giản nhất.
