# 11.11 - SSE, streaming và giới hạn tài nguyên

> **Tóm tắt:** Ba chủ đề nối tiếp Module 11, kèm điều kiện. **Server-Sent Events** (SSE): với nhu cầu chỉ đẩy một chiều từ server, nó đơn giản hơn SignalR đáng kể, và từ .NET 10 có sẵn `TypedResults.ServerSentEvents` — nhưng khi chạy nhiều instance, bạn phải tự dựng phần phát tin giữa các instance. **Streaming** trong SignalR cho client thấy dữ liệu từ phần tử đầu tiên thay vì chờ cả mảng. **Giới hạn kích thước message và số kết nối** là thứ bật ngay khi lên production: một message vượt giới hạn làm server **đóng cả kết nối**, và thiếu giới hạn thì một client có thể chiếm hết bộ nhớ server.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Chọn giữa SignalR và Server-Sent Events theo số chiều giao tiếp và số instance.
- Dùng streaming cho dữ liệu dài và huỷ được giữa chừng.
- Đặt giới hạn kích thước message và số kết nối mỗi người dùng.
- Biết mình đang ở đâu so với những chủ đề còn lại của module.

**Cần biết trước:** [bài 11.1](11.1-why-real-time-matters.md) (SSE, WebSocket), [bài 11.3](11.3-setup-signalr-server.md) (cấu hình Hub), [bài 6.6](../../stage-02-csharp-professional/module-06-async-programming/6.6-async-patterns.md) (`IAsyncEnumerable`). Đây là bài đọc thêm, phần lớn nội dung dành cho hệ thống đã chạy production.

## Nội dung bài học

### 11.11.1 — Server-Sent Events: cân nhắc trước

**Điều kiện kích hoạt:** chỉ cần đẩy dữ liệu **một chiều** từ server.

Từ .NET 10, endpoint SSE chỉ cần trả về `TypedResults.ServerSentEvents` với một nguồn `IAsyncEnumerable`. `INotificationStream` là service bạn tự viết, như ở bài 2 của [bài 11.1](11.1-why-real-time-matters.md):

```csharp
app.MapGet("/api/v1/notifications/stream",
    (HttpContext ctx, INotificationStream stream, CancellationToken ct) =>
        TypedResults.ServerSentEvents(
            stream.SubscribeAsync(ctx.User.FindFirst("sub")!.Value, ct),
            eventType: "notification"))
   .RequireAuthorization();
```

```javascript
const source = new EventSource('/api/v1/notifications/stream');
source.addEventListener('notification', e => render(JSON.parse(e.data)));
// Tự động kết nối lại khi đứt — không cần cấu hình gì
```

| | SignalR | Server-Sent Events |
|---|---|---|
| Hướng | **Hai chiều** | Một chiều (server → client) |
| Giao thức | WebSocket, SSE, long polling | **HTTP thường** |
| Nhiều instance | Thêm Redis backplane (vài dòng cấu hình) | **Tự dựng** pub/sub giữa các instance |
| Cấu hình proxy | Cần header `Upgrade` cho WebSocket | Tắt buffer (`X-Accel-Buffering: no` hoặc `proxy_buffering off`) |
| Tự kết nối lại | Có (cấu hình) | **Có sẵn** trong trình duyệt |
| Quản lý nhóm, gửi theo user | **Có sẵn** | Tự làm |
| Header `Authorization` từ trình duyệt | Không qua WebSocket (dùng query string) | Không (`EventSource` không cho đặt header) |

Với thông báo, tiến độ job, hoặc bảng số liệu cập nhật — những thứ chỉ đi **một chiều**, chạy **một instance** — SSE gọn hơn hẳn. Khi đã nhiều instance hoặc cần nhóm, bài 1 cho thấy kết luận đảo chiều.

**Hạn chế của SSE:** trên HTTP/1.1, trình duyệt giới hạn 6 kết nối mỗi tên miền, và một SSE chiếm một kết nối. Trên HTTP/2 giới hạn đó biến mất ([bài 11.1](11.1-why-real-time-matters.md), bài 3).

### 11.11.2 — Streaming trong SignalR

**Điều kiện kích hoạt:** gửi một chuỗi dữ liệu dài mà client muốn xử lý dần.

Một Hub method trả `IAsyncEnumerable<T>` là một **stream**: SignalR gửi từng phần tử ngay khi nó được `yield return`.

```csharp
public sealed class NotificationHub(CrmDbContext db) : Hub<INotificationClient>
{
    public async IAsyncEnumerable<LeadDto> StreamLeads(
        [EnumeratorCancellation] CancellationToken ct)
    {
        await foreach (var lead in db.Leads.AsNoTracking().AsAsyncEnumerable().WithCancellation(ct))
            yield return new LeadDto(lead.Id, lead.Name);
    }
}
```

```javascript
const subscription = connection.stream('StreamLeads').subscribe({
    next: lead => appendRow(lead),          // hiển thị ngay từng dòng
    complete: () => console.log('Xong'),
    error: err => console.error(err)
});
// subscription.dispose() để huỷ giữa chừng
```

Khác biệt so với gửi một mảng lớn: client thấy dữ liệu **ngay từ bản ghi đầu tiên** thay vì chờ toàn bộ, và server không phải giữ cả tập dữ liệu trong bộ nhớ ([bài 5.9](../../stage-02-csharp-professional/module-05-advanced-csharp/5.9-advanced-notes.md)).

`[EnumeratorCancellation]` nối token huỷ của SignalR vào thân phương thức. Client gọi `dispose()` thì token bị huỷ, `await foreach` dừng, và truy vấn database dừng theo.

**Client cũng stream lên server được** — hữu ích cho dữ liệu cảm biến hay nhập liệu liên tục. Hub method nhận một tham số `IAsyncEnumerable<T>` (hoặc `ChannelReader<T>`):

```csharp
public async Task UploadReadings(IAsyncEnumerable<SensorReading> readings)
{
    await foreach (var r in readings)
        await store.AppendAsync(r);
}
```

### 11.11.3 — Giới hạn message và kết nối: bật ngay

**Điều kiện kích hoạt:** ngay khi đưa SignalR lên production.

```csharp
builder.Services.AddSignalR(options =>
{
    options.MaximumReceiveMessageSize = 32 * 1024;          // 32 KB, cũng là mặc định
    options.StreamBufferCapacity = 10;
    options.EnableDetailedErrors = builder.Environment.IsDevelopment();
});
```

| Tuỳ chọn | Vì sao |
|---|---|
| `MaximumReceiveMessageSize` | Chặn client gửi payload khổng lồ làm cạn bộ nhớ |
| `StreamBufferCapacity` | Giới hạn số item đệm cho mỗi stream từ client |
| `EnableDetailedErrors` | Bật trên production là gửi tên kiểu và message exception cho client ([bài 11.3](11.3-setup-signalr-server.md)) |

Giữ nhịp và timeout (hai cặp số, quy tắc gấp đôi) đã ở [bài 11.2](11.2-signalr-architecture.md).

**Giới hạn số kết nối mỗi người dùng** cũng đáng có, vì một script mở 1.000 kết nối là cách tấn công rất rẻ. `IPresenceTracker` ở [bài 11.9](11.9-presence-online-offline-status.md) đã biết số kết nối còn sống của một người; thêm một method đếm:

```csharp
public override async Task OnConnectedAsync()
{
    var userId = Context.UserIdentifier!;

    if (await connectionCounter.CountAsync(userId) >= 5)    // tối đa 5 thiết bị hoặc tab
    {
        Context.Abort();
        return;
    }

    await base.OnConnectedAsync();
}
```

`connectionCounter` là service bạn tự viết; với Redis thì nó trả về số phần tử còn sống trong Set `presence:user:{userId}`. Ở tầng hạ tầng, giới hạn thêm số kết nối mỗi IP tại reverse proxy.

### 11.11.5 — Rà lại code của bạn

**Danh sách rà soát SignalR nâng cao**

- [ ] Đã cân nhắc Server-Sent Events nếu chỉ cần đẩy một chiều trên một instance.
- [ ] Biết SSE nhiều instance cần tự dựng pub/sub.
- [ ] MaximumReceiveMessageSize được đặt có chủ đích, không nới lên hàng MB.
- [ ] Dữ liệu lớn đi qua HTTP upload, không đi qua SignalR.
- [ ] Stream server có `[EnumeratorCancellation]` và truyền token xuống truy vấn.
- [ ] EnableDetailedErrors tắt trên production.
- [ ] Có giới hạn số kết nối mỗi người dùng.

## Bài tập áp dụng

#### Bài 1 — Đếm chi phí của SSE so với SignalR

Cài cùng một tính năng thông báo bằng cả hai và so sánh lượng code cần thiết.

**Tiêu chí hoàn thành:** bạn so cả **hai kịch bản** — một instance và nhiều instance — vì kết luận đảo chiều giữa hai kịch bản.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Với một instance, SignalR làm hộ bạn những thứ bạn chưa cần. Với nhiều instance, nó làm hộ đúng những thứ khó nhất.

**Lời giải — kịch bản một instance.**

SSE: endpoint ở mục 11.11.1 (khoảng 5 dòng nhờ `TypedResults.ServerSentEvents`), cộng `INotificationStream` đọc từ một `Channel` theo người dùng, cộng hai dòng `EventSource` ở client.

SignalR:

```csharp
builder.Services.AddSignalR();
app.MapHub<NotificationHub>("/hubs/notifications").RequireAuthorization();
```

```csharp
public interface INotificationClient { Task ReceiveNotification(NotificationDto dto); }

public class NotificationHub : Hub<INotificationClient> { }
```

```js
const c = new signalR.HubConnectionBuilder().withUrl('/hubs/notifications')
    .withAutomaticReconnect().build();
c.on('ReceiveNotification', showToast);
await c.start();
```

| | SSE | SignalR |
|---|---|---|
| Code phía server | Endpoint + service phát tin theo user | Hub + `AddSignalR`/`MapHub` |
| Gói phụ thuộc phía client | **0** | 1 gói npm |
| Cấu hình proxy | Tắt buffer | `Upgrade`, `Connection`, `proxy_read_timeout` |

**Gần như hoà, và SSE nhỉnh hơn ở chỗ không thêm phụ thuộc nào.**

**Kịch bản nhiều instance — kết luận đảo chiều.**

SignalR chỉ thêm một khối:

```csharp
builder.Services.AddSignalR()
    .AddStackExchangeRedis(cs, o => o.Configuration.AbortOnConnectFail = false);
```

Xong: gửi theo người dùng, theo nhóm, xuyên instance, tự dọn khi ngắt.

Với SSE, bạn phải tự viết toàn bộ phần đó:

```csharp
// Phác thảo — mỗi instance giữ kênh của các client nó đang phục vụ
// và nghe Redis pub/sub để nhận tin từ instance khác
public sealed class RedisNotificationFanout(IConnectionMultiplexer redis)
{
    private readonly ConcurrentDictionary<string, Channel<NotificationDto>> _local = new();
    private static readonly RedisChannel Topic = RedisChannel.Literal("notify");

    public async Task StartAsync()
    {
        await redis.GetSubscriber().SubscribeAsync(Topic, (_, msg) =>
        {
            var env = JsonSerializer.Deserialize<Envelope>(msg.ToString())!;
            if (_local.TryGetValue(env.UserId, out var ch)) ch.Writer.TryWrite(env.Payload);
        });
    }

    public Task PublishAsync(string userId, NotificationDto n) =>
        redis.GetSubscriber().PublishAsync(Topic, JsonSerializer.Serialize(new Envelope(userId, n)));

    // Còn phải tự viết: đăng ký và dọn kênh khi client ngắt,
    // một người nhiều tab, gửi theo nhóm, xử lý Redis mất kết nối...
}

public sealed record Envelope(string UserId, NotificationDto Payload);
```

| | SSE | SignalR |
|---|---|---|
| Code cho phần phân tán | Một lớp riêng, còn nhiều việc tự làm | **Vài dòng cấu hình** |
| Gửi theo nhóm | Tự viết | Có sẵn |
| Nhiều thiết bị một người | Tự viết | `Clients.User` |
| Tự lùi transport khi bị chặn | Không có | Có sẵn |

**Kết luận theo kịch bản:**

- **Một instance, một chiều, không muốn thêm phụ thuộc** — SSE gọn hơn và đủ dùng. Ví dụ: trang theo dõi tiến độ một job, log đẩy về trang quản trị.
- **Nhiều instance, hoặc cần hai chiều, hoặc cần nhóm** — SignalR rẻ hơn hẳn, vì thứ bạn phải tự viết chính là phần khó và dễ sai nhất.

Sai lầm hay gặp là chọn SSE vì "gọn hơn" ở giai đoạn một instance, rồi phải viết lại khi scale ra — đúng lúc hệ thống đang chịu tải.

</details>

#### Bài 2 — Streaming mười nghìn phần tử

Viết một Hub method trả `IAsyncEnumerable<int>` gồm 10.000 phần tử, đo thời điểm client nhận phần tử đầu tiên và phần tử cuối cùng.

**Tiêu chí hoàn thành:** bạn nêu được streaming khác gì với việc gửi một mảng lớn, và một trường hợp nó **không** phù hợp.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** So sánh thời điểm client nhận được **phần tử đầu tiên**, không phải thời điểm nhận xong.

**Lời giải:**

```csharp
public async IAsyncEnumerable<int> StreamNumbers(int n, [EnumeratorCancellation] CancellationToken ct)
{
    for (var i = 1; i <= n; i++)
    {
        if (i % 100 == 0) await Task.Yield();     // nhường luồng, giả lập việc đọc dần
        yield return i;
    }
}
```

```js
const t0 = performance.now();
let first = null, n = 0;
await new Promise(resolve => connection.stream('StreamNumbers', 10000).subscribe({
    next: () => { if (n++ === 0) first = performance.now() - t0; },
    complete: resolve,
    error: resolve
}));
console.log(`stream: phần tử đầu sau ${first.toFixed(0)} ms, đủ ${n} phần tử sau ${(performance.now() - t0).toFixed(0)} ms`);
```

Output thật trên máy local (server và client cùng máy, phần tử rất nhỏ):

```text
stream: phần tử đầu sau 10 ms, đủ 10000 phần tử sau 56 ms
```

Với dữ liệu thật đọc từ database qua mạng, mọi con số đều lớn hơn, nhưng khoảng cách giữa "phần tử đầu" và "phần tử cuối" mới là thứ quan trọng: giao diện có dữ liệu để vẽ ngay từ mốc đầu.

**So với gửi một mảng lớn:**

| | Gửi mảng | Streaming |
|---|---|---|
| Byte đầu tiên tới client | Sau khi gom xong **tất cả** | **Ngay phần tử đầu** |
| Bộ nhớ server | Cả mảng | Một phần tử đang xử lý |
| Bộ nhớ client | Cả mảng | Tăng dần |
| Huỷ giữa chừng | Không làm được | **`subscription.dispose()`** |

Dòng cuối đáng chú ý: người dùng đóng bảng thì `dispose()` huỷ `CancellationToken` ở server, `await foreach` dừng, và truy vấn database bị huỷ theo. Với cách gửi mảng, server vẫn chạy hết rồi mới phát hiện không ai cần nữa.

**Cái bẫy thường gặp — `[EnumeratorCancellation]`.** Thiếu attribute này, token huỷ của stream **không tới được** thân phương thức, và huỷ không có tác dụng — đúng vấn đề ở [bài 5.9](../../stage-02-csharp-professional/module-05-advanced-csharp/5.9-advanced-notes.md).

**Khi nào streaming KHÔNG phù hợp:**

Khi client cần **toàn bộ dữ liệu trước khi làm được gì**. Ví dụ: tải danh sách để sắp xếp rồi mới hiển thị, hoặc tính một tổng từ tất cả bản ghi. Lúc đó streaming chỉ thêm phức tạp mà không đem lại gì — client vẫn phải đợi phần tử cuối.

Và với dữ liệu thật sự lớn, câu hỏi đúng thường không phải "streaming hay không" mà là **"vì sao client cần 10.000 bản ghi?"**. Phân trang hoặc tổng hợp phía server gần như luôn là câu trả lời tốt hơn — xem [bài 9.4](../module-09-web-api-professional/9.4-pagination-filtering-sorting.md).

**Streaming hợp nhất cho:** kết quả tính toán dần (tiến độ import), dữ liệu đến theo thời gian (log trực tiếp), và bảng lớn mà người dùng bắt đầu đọc được ngay từ dòng đầu.

</details>

#### Bài 3 — Giới hạn kích thước message

Gửi một message 1 MB từ client và xác nhận server từ chối. Làm hai lần: `EnableDetailedErrors` tắt và bật.

**Tiêu chí hoàn thành:** bạn nêu được server làm gì với **kết nối** (không chỉ với message), vì sao giới hạn mặc định **32 KB** là hợp lý, và điều gì xảy ra nếu bạn nới nó lên quá tay.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Nghĩ xem bộ nhớ cần bao nhiêu khi 1.000 client cùng gửi một message lớn.

**Lời giải — gửi message vượt giới hạn:**

```js
connection.onclose(e => console.log('onclose:', e?.message));
try { await connection.invoke('Echo', 'x'.repeat(1024 * 1024)); }    // 1 MB
catch (e) { console.log('Echo 1MB ->', e.message); }
```

Output thật, `EnableDetailedErrors` tắt:

```text
onclose: Server returned an error on close: Connection closed with an error.
Echo 1MB -> Server returned an error on close: Connection closed with an error.
```

`EnableDetailedErrors` bật:

```text
Echo 1MB -> Server returned an error on close: Connection closed with an error. InvalidDataException: The maximum message size of 32768B was exceeded. The message size can be configured in AddHubOptions.
```

**Kết nối bị đóng**, không chỉ message bị từ chối — SignalR coi đây là lỗi giao thức. Với `withAutomaticReconnect`, client sẽ nối lại và người dùng thấy một lần "đang kết nối lại" khó hiểu.

Ở server, lỗi này chỉ được ghi ở mức **Debug**, nên với cấu hình log mặc định bạn không thấy gì. Bật `"Microsoft.AspNetCore.SignalR": "Debug"` trong `appsettings.Development.json` thì thấy:

```text
dbug: Microsoft.AspNetCore.SignalR.HubConnectionHandler[2]
      Error when processing requests.
      System.IO.InvalidDataException: The maximum message size of 32768B was exceeded. The message size can be configured in AddHubOptions.
```

**Vì sao 32 KB là con số hợp lý.** Server phải đệm trọn một message trước khi xử lý, cho **mỗi kết nối đang nhận dở**:

```text
1.000 client đồng thời × 32 KB = 32 MB     (chấp nhận được)
1.000 client đồng thời × 1 MB  = 1 GB      (đủ để bị OOM killer giết)
```

Và đây là bộ nhớ do **client kiểm soát**: bất kỳ ai cũng mở được nhiều kết nối rồi gửi message lớn. Không có giới hạn chặt, đó là một đường tấn công từ chối dịch vụ rất rẻ — kẻ tấn công chỉ tốn băng thông, còn bạn tốn RAM.

Ngoài ra, SignalR là kênh cho **tin nhắn nhỏ và thường xuyên**. Một message 1 MB chiếm kênh đủ lâu để làm trễ mọi tin khác trên cùng kết nối, vì lời gọi từ một client được xử lý tuần tự — xem [bài 11.3](11.3-setup-signalr-server.md).

**Nới giới hạn khi thật sự cần, và nới có chủ đích:**

```csharp
builder.Services.AddSignalR(o => o.MaximumReceiveMessageSize = 128 * 1024);   // 128 KB, không phải 10 MB
```

**Nếu bạn thấy mình muốn nới lên hàng MB, gần như chắc chắn bạn đang dùng sai công cụ.** Dữ liệu lớn nên đi qua HTTP:

```js
// SAI — đẩy cả file qua SignalR
await connection.invoke('UploadFile', base64Content);

// ĐÚNG — upload qua HTTP, báo kết quả qua SignalR
const { id } = await fetch('/api/v1/files', { method: 'POST', body: formData })
    .then(r => r.json());
// server xử lý xong sẽ đẩy FileProcessed(id) qua hub
```

Cách này tốt hơn ở ba điểm: HTTP có sẵn cơ chế upload theo luồng không tốn bộ nhớ ([bài 9.5](../module-09-web-api-professional/9.5-file-upload-and-download.md)), có thể tiếp tục khi đứt giữa chừng, và không chặn kênh real-time.

</details>

## Tự kiểm tra

<details>
<summary>Khi nào Server-Sent Events đủ thay cho SignalR?</summary>

Khi chỉ cần đẩy dữ liệu một chiều từ server, như thông báo, tiến độ job hay bảng số liệu, và chạy một instance. SSE chạy trên HTTP thường, trình duyệt tự kết nối lại, và từ .NET 10 có sẵn TypedResults.ServerSentEvents. Nhiều instance thì phải tự dựng pub/sub giữa các instance, lúc đó SignalR với backplane rẻ hơn.

</details>

<details>
<summary>Hạn chế của SSE là gì?</summary>

Nó chỉ một chiều, EventSource không cho đặt header Authorization, và trên HTTP/1.1 trình duyệt giới hạn sáu kết nối mỗi tên miền mà một SSE chiếm một kết nối. Trên HTTP/2 giới hạn số kết nối biến mất.

</details>

<details>
<summary>Streaming khác gửi một mảng lớn thế nào?</summary>

Client thấy dữ liệu ngay từ phần tử đầu tiên thay vì chờ toàn bộ, server không phải giữ cả tập dữ liệu trong bộ nhớ, và client huỷ được giữa chừng bằng dispose, làm token ở server bị huỷ nếu phương thức có [EnumeratorCancellation].

</details>

<details>
<summary>Client gửi message vượt MaximumReceiveMessageSize thì sao?</summary>

Server đóng cả kết nối, không chỉ từ chối message đó. Client nhận "Connection closed with an error", kèm tên lỗi InvalidDataException nếu EnableDetailedErrors bật. Ở server, lỗi chỉ được log ở mức Debug.

</details>

<details>
<summary>Vì sao nên giới hạn số kết nối mỗi người dùng?</summary>

Vì mở nhiều kết nối là cách tấn công rất rẻ: mỗi kết nối chiếm bộ nhớ và bộ đệm trên server. Đếm kết nối còn sống của người dùng (ví dụ từ presence trong Redis) và Abort khi vượt ngưỡng, cộng giới hạn số kết nối mỗi IP ở reverse proxy.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **Cân nhắc SSE trước** cho nhu cầu một chiều trên một instance; nhiều instance thì SignalR với backplane rẻ hơn.
2. **Streaming** cho dữ liệu đến dần, kèm `[EnumeratorCancellation]` để huỷ được.
3. **Giới hạn kích thước message và số kết nối** là thứ phải bật ngay trên production.
