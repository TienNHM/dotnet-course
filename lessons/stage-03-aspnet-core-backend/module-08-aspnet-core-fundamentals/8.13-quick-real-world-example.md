# 8.13 - Tình huống: API lộ stack trace ra ngoài

> **Tóm tắt:** Một lỗi vừa là vấn đề **trải nghiệm** vừa là vấn đề **bảo mật**: API production trả về `500` kèm **chi tiết exception** — thông điệp có tên máy chủ database, stack trace có đường dẫn file trên máy build và tên lớp nội bộ. Người dùng thấy một mớ chữ khó hiểu; kẻ tấn công thấy một bản đồ hệ thống. Bài này là một tình huống ngắn áp dụng [bài 8.8](8.8-global-exception-handling.md): tìm ba chỗ rò rỉ (thân phản hồi, header, và sự khác biệt giữa 403 với 404), sửa từng chỗ, rồi nối `traceId` trong phản hồi với dòng log tương ứng để đội vận hành vẫn có đủ thông tin.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Kiểm tra một API xem có rò rỉ thông tin nội bộ qua phản hồi lỗi, header và mã trạng thái không.
- Giải thích vì sao `UseDeveloperExceptionPage` đặt vô điều kiện là lỗ hổng.
- Thiết kế phản hồi để kẻ dò tìm không phân biệt được "không có" với "không phải của bạn".
- Tìm đúng dòng log từ `traceId` mà người dùng gửi lại.

**Cần biết trước:** [bài 8.8](8.8-global-exception-handling.md) (`IExceptionHandler`, cây exception nghiệp vụ), [bài 8.7](8.7-logging-with-serilog.md) (Serilog, JSON log), [bài 8.1](8.1-aspnet-core-architecture.md) (môi trường `ASPNETCORE_ENVIRONMENT`).

## Nội dung bài học

### 8.13.1 — Sự cố

Một bản build đưa lên production có dòng `app.UseDeveloperExceptionPage();` nằm ngoài khối `if (app.Environment.IsDevelopment())`. Một endpoint gặp lỗi database. Chạy thật trên .NET 10, môi trường Production, gọi bằng `curl` (rút gọn chuỗi exception):

```text
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json
Server: Kestrel

{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"System.InvalidOperationException","status":500,
 "detail":"Invalid object name 'Leads_Old'. Host=prod-db-01;Database=crm;Username=crm_app",
 "exception":{"details":"System.InvalidOperationException: Invalid object name 'Leads_Old'. ...\r\n
   at Program.<>c.<<Main>$>b__0_5() in C:\\Users\\tienn\\...\\Program.cs:line 34\r\n ...",
 "headers":{"Accept":["*/*"],"Host":["localhost:5315"],"User-Agent":["curl/8.17.0"]},
 "path":"/sys","endpoint":"HTTP: GET /sys","routeValues":{}},
 "traceId":"00-2b580758fbdf673149f99c5b962d2557-90afd5f9f6c33be7-00"}
```

Trang lỗi cho lập trình viên trả JSON khi client không phải trình duyệt, và HTML đầy đủ khi là trình duyệt. Cả hai đều chứa:

| Thông tin | Giá trị với kẻ tấn công |
|---|---|
| Thông điệp exception: tên bảng, tên máy chủ database, tài khoản | Mục tiêu cụ thể, nửa thông tin đăng nhập |
| Đường dẫn file trên máy build (`C:\Users\tienn\...`) | Tên người dùng, cấu trúc hệ thống build |
| Tên lớp và phương thức | Bản đồ kiến trúc nội bộ |
| Toàn bộ header của request | Nếu có cookie hay token, chúng bị phản chiếu lại |

### 8.13.2 — Hai nguyên nhân thường gặp

```csharp
// Nguyên nhân 1 — trang lỗi của môi trường phát triển chạy trên production
app.UseDeveloperExceptionPage();     // SAI: KHÔNG bao giờ đặt vô điều kiện
```

Thực ra trên .NET 10 bạn **không cần** gọi dòng này: `WebApplication` tự bật trang lỗi cho lập trình viên khi môi trường là Development. Xoá nó đi là cách sửa đơn giản nhất.

```csharp
// Nguyên nhân 2 — SAI: try/catch rải rác trả về chi tiết exception
try
{
    return Ok(await _service.GetAsync(id, ct));
}
catch (Exception ex)
{
    return StatusCode(500, new { error = ex.ToString() });     // LỘ HẾT
}
```

Nguyên nhân thứ hai tệ hơn vì nó **rải khắp codebase** — sửa một chỗ không đủ, và chỗ mới sẽ xuất hiện khi có người viết controller tiếp theo. Cách sửa là xoá các `try/catch` đó và để `GlobalExceptionHandler` của [bài 8.8](8.8-global-exception-handling.md) xử lý tập trung.

Cùng endpoint ở trên, sau khi bỏ `UseDeveloperExceptionPage` và dùng `GlobalExceptionHandler`, kết quả chạy thật:

```text
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"Lỗi hệ thống","status":500,
 "instance":"/sys","traceId":"00-2f0ed4d59515bb39ed8b7b83f2ce83a5-82b9b30d347997f3-00"}
```

### 8.13.3 — Lỗi nghiệp vụ và lỗi hệ thống

| | Lỗi nghiệp vụ | Lỗi hệ thống |
|---|---|---|
| Ví dụ | "Lead đã được chốt, không sửa được" | Lỗi kết nối database, `NullReferenceException` |
| Người dùng sửa được không | **Có** | Không |
| Có nên nói rõ không | **Có — nói rõ càng tốt** | **Không — chỉ đưa mã tra cứu** |
| Mã trạng thái | 4xx | 5xx |
| Mức log | `Warning`, không cần stack trace | `Error`, kèm exception đầy đủ |

**Giấu lỗi nghiệp vụ là tệ với người dùng:** "Đã xảy ra lỗi" khi thực ra là "Email này đã được đăng ký" khiến họ thử lại vô vọng và gọi hỗ trợ. **Lộ lỗi hệ thống là tệ với bảo mật.**

Cách phân biệt trong code: lỗi nghiệp vụ dùng exception riêng kế thừa `DomainException` ([bài 8.8](8.8-global-exception-handling.md)), mọi thứ khác rơi vào nhánh mặc định và bị giấu. Khi viết `switch` theo kiểu exception, đặt kiểu cụ thể **trước** kiểu cha:

```csharp
// ĐÚNG — cụ thể trước, tổng quát sau
var status = exception switch
{
    NotFoundException  => StatusCodes.Status404NotFound,
    ConflictException  => StatusCodes.Status409Conflict,
    DomainException    => StatusCodes.Status400BadRequest,
    _                  => StatusCodes.Status500InternalServerError
};
```

Đảo `DomainException` lên đầu thì nhánh `NotFoundException` không bao giờ khớp, và trình biên dịch báo lỗi:

```text
error CS8510: The pattern is unreachable. It has already been handled by a previous arm of the switch expression
or it is impossible to match.
```

### 8.13.4 — Header và mã trạng thái cũng lộ thông tin

**Header `Server`.** Kestrel mặc định gửi `Server: Kestrel`, cho biết ngay bạn chạy ASP.NET Core. Tắt nó:

```csharp
builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false);
```

Chạy lại, phản hồi không còn header `Server`. (Header `X-Powered-By: ASP.NET` mà bạn có thể thấy trên mạng là do **IIS** thêm vào, không phải Kestrel; chạy sau IIS thì tắt nó trong `web.config`.)

**403 so với 404.** Giả sử lead 1 tồn tại nhưng thuộc công ty (tenant) khác, còn lead 999999 không tồn tại. Nếu API trả `403 Forbidden` cho trường hợp đầu và `404 Not Found` cho trường hợp sau, kẻ tấn công chỉ cần duyệt id từ 1 trở đi là biết id nào **có thật** và ước lượng được hệ thống có bao nhiêu lead. Kiểu dò này gọi là *enumeration* (liệt kê).

Cách sửa: trả **404 cho cả hai**, bằng cách lọc tenant **trong** truy vấn thay vì lấy bản ghi về rồi mới kiểm tra quyền. Ví dụ dùng EF Core ([bài 8.10](8.10-ef-core-minimal.md)), `currentUser.TenantId` lấy từ người dùng đã đăng nhập:

```csharp
var lead = await db.Leads
    .Where(l => l.Id == id && l.TenantId == currentUser.TenantId)   // lọc tenant TRONG truy vấn
    .FirstOrDefaultAsync(ct);

return lead is null ? Results.NotFound() : Results.Ok(lead);
```

"Không có" và "không phải của bạn" đi cùng một đường code, cùng một câu SQL, cùng mã trạng thái — nên cũng khó phân biệt qua thời gian phản hồi.

### 8.13.5 — Nối lỗi với log

Người dùng chỉ có `traceId`. Nó phải dẫn bạn tới đúng dòng log. `traceId` mà `ProblemDetails` trả về có dạng chuẩn [W3C Trace Context](https://www.w3.org/TR/trace-context/):

```text
00-b63036a8d4861a62b736ae7f2f3912ee-7b6bf909ae81f948-00
│  │                                │                └─ cờ
│  │                                └─ span id: một chặng xử lý
│  └─ trace id: TOÀN BỘ hành trình của request
└─ phiên bản
```

Serilog trên .NET 10 tự ghi trace id vào trường `@tr` của mọi dòng log trong request ([bài 8.7](8.7-logging-with-serilog.md)). Phần giữa của `traceId` chính là giá trị cần tìm. Khi nhiều service gọi nhau qua `HttpClient`, ASP.NET Core tự truyền trace id qua header `traceparent`, nên log của mọi service trong cùng một request có chung trace id; [bài 18.5](../../stage-05-senior-engineering/module-18-microservices/18.5-observability-three-pillars.md) dạy phần này.

### 8.13.6 — Rà lại code của bạn

**Danh sách rà soát rò rỉ thông tin**

- [ ] Không có lời gọi `UseDeveloperExceptionPage()` nào trong `Program.cs` (để `WebApplication` tự bật ở Development).
- [ ] Không có `try/catch` nào trả `ex.Message` hay `ex.ToString()` cho client.
- [ ] `switch` theo kiểu exception đặt kiểu cụ thể trước kiểu cha.
- [ ] Lỗi hệ thống chỉ trả `title`, `status`, `traceId`; lỗi nghiệp vụ nói rõ nguyên nhân.
- [ ] Header `Server` đã tắt.
- [ ] Tài nguyên của tenant khác trả 404, không phải 403.
- [ ] `traceId` trong phản hồi tìm được trong log.
- [ ] Đã thử gây lỗi trên môi trường Production (hoặc staging giống production) và đọc kỹ phản hồi.

## Bài tập áp dụng

#### Bài 1 — Kiểm tra rò rỉ

Trên máy của bạn, tạo một API có endpoint ném `InvalidOperationException` với thông điệp chứa một chuỗi giống chuỗi kết nối. Chạy ở môi trường **Production** (`dotnet run -- --environment Production`; tham số sau dấu `--` truyền cho ứng dụng và thắng cả `launchSettings.json`) trong hai cấu hình: có `app.UseDeveloperExceptionPage();` vô điều kiện, và có `GlobalExceptionHandler` của bài 8.8. Gọi bằng `curl -i` và đọc **cả header lẫn body**.

**Tiêu chí hoàn thành:** bạn liệt kê được những gì bị lộ ở cấu hình thứ nhất, xác nhận cấu hình thứ hai không lộ chúng, và tắt được header `Server`.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Đọc cả header phản hồi, không chỉ phần thân. `curl -i` in cả hai.

**Lời giải.**

```csharp
app.MapGet("/sys", () =>
{
    throw new InvalidOperationException(
        "Invalid object name 'Leads_Old'. Host=prod-db-01;Database=crm;Username=crm_app");
});
```

Cấu hình thứ nhất cho kết quả như mục 8.13.1: thông điệp exception, stack trace có đường dẫn trên máy build, tên lớp, toàn bộ header request, và header `Server: Kestrel`. Cấu hình thứ hai cho kết quả như cuối mục 8.13.2: chỉ `title`, `status`, `instance`, `traceId`.

Thêm `builder.WebHost.ConfigureKestrel(o => o.AddServerHeader = false);` và chạy lại `curl -i`: header `Server` biến mất.

**Danh sách rà nhanh, chạy được trên staging trong hai phút** (thay địa chỉ bằng API của bạn):

```bash
# 1. Header có lộ công nghệ không?
curl -sI https://staging.example.com/api/leads | grep -iE "^server|x-powered|x-aspnet"

# 2. Lỗi 500 có lộ chi tiết không?
curl -s https://staging.example.com/api/leads/abc | grep -oE "   at [A-Za-z.]+|Host=|Password=" | head
```

**Điều quan trọng nhất về trang lỗi cho lập trình viên:** nó chỉ an toàn khi biến `ASPNETCORE_ENVIRONMENT` đúng. Đặt nhầm `Development` trên staging hay production là lộ toàn bộ — và đó là một dòng cấu hình triển khai, không có test nào trong code bảo vệ. Vì vậy test trong bài tập 3 của [bài 8.12](8.12-mini-case-study.md) nên có một test gọi endpoint lỗi và kiểm tra body không chứa `   at ` hay `Host=`, chạy với môi trường Production.

</details>

#### Bài 2 — 403 so với 404

Viết endpoint `GET /api/leads/{id}` với dữ liệu trong bộ nhớ: mỗi lead có `TenantId`, người dùng hiện tại có `TenantId = 1` (viết cứng cho bài tập). Bản đầu trả 403 khi lead thuộc tenant khác và 404 khi không tồn tại. Sửa để kẻ dò tìm không phân biệt được hai trường hợp.

**Tiêu chí hoàn thành:** sau khi sửa, lead của tenant khác và lead không tồn tại cho **cùng mã trạng thái và cùng body**.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Câu hỏi không phải "bản ghi có tồn tại không" mà là "bản ghi có tồn tại **trong phạm vi người này được thấy** không".

**Lời giải.**

```csharp
// Lead.cs
public record Lead(int Id, int TenantId, string FullName);
```

```csharp
// Program.cs
const int currentTenantId = 1;                          // bài tập: viết cứng
var leads = new List<Lead> { new(1, 2, "Lead của tenant 2"), new(2, 1, "Lead của tenant 1") };

// SAI — lộ việc lead có tồn tại hay không
app.MapGet("/v1/leads/{id:int}", (int id) =>
{
    var lead = leads.FirstOrDefault(l => l.Id == id);
    if (lead is null) return Results.NotFound();
    if (lead.TenantId != currentTenantId) return Results.StatusCode(403);   // <- khác biệt lộ ra ở đây
    return Results.Ok(lead);
});

// ĐÚNG — lọc tenant ngay trong điều kiện tìm
app.MapGet("/v2/leads/{id:int}", (int id) =>
    leads.FirstOrDefault(l => l.Id == id && l.TenantId == currentTenantId) is { } lead
        ? Results.Ok(lead)
        : Results.NotFound());
```

Kết quả chạy thật trên .NET 10:

```text
GET /v1/leads/1        -> 403      <- lộ: lead 1 có tồn tại
GET /v1/leads/999999   -> 404
GET /v2/leads/1        -> 404
GET /v2/leads/999999   -> 404      <- giống hệt dòng trên
GET /v2/leads/2        -> 200
```

Trong ứng dụng thật đã cấu hình xác thực, bạn sẽ viết `Results.Forbid()` thay cho `Results.StatusCode(403)`; ví dụ này chưa có xác thực nên trả thẳng mã 403.

Với database thật, điều kiện tenant nằm trong câu `WHERE` như ví dụ EF Core ở mục 8.13.4; [bài 13.10](../../stage-04-database-production/module-13-entity-framework-core/13.10-global-query-filters.md) chỉ cách để EF Core tự thêm điều kiện này cho mọi truy vấn.

</details>

#### Bài 3 — Nối log

Cấu hình Serilog ghi JSON ra console ([bài 8.7](8.7-logging-with-serilog.md)) cùng `GlobalExceptionHandler` của bài 8.8. Gây một lỗi 500, lấy `traceId` từ phản hồi, và tìm đúng dòng log bằng mã đó.

**Tiêu chí hoàn thành:** bạn tìm được dòng log `Error` có exception đầy đủ từ `traceId` trong phản hồi.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** `traceId` có bốn phần ngăn bởi dấu `-`. Phần thứ hai là trace id, và Serilog ghi nó vào trường `@tr`.

**Lời giải.** Chạy thật trên .NET 10 với Serilog.AspNetCore 10, endpoint `/api/leads/{id}` ném exception:

```bash
curl -s localhost:5000/api/leads/8842
```

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"Lỗi hệ thống","status":500,
 "instance":"/api/leads/8842","traceId":"00-b63036a8d4861a62b736ae7f2f3912ee-7b6bf909ae81f948-00"}
```

Tìm phần giữa trong log (ghi log ra file `log.json` bằng `dotnet run > log.json`):

```bash
grep b63036a8d4861a62b736ae7f2f3912ee log.json
```

```powershell
Select-String b63036a8d4861a62b736ae7f2f3912ee log.json
```

Dòng log tìm được (rút gọn):

```json
{"@t":"2026-10-18T03:26:46.0168863Z","@mt":"Lỗi chưa xử lý tại {Path}","@l":"Error",
 "@x":"System.InvalidOperationException: Invalid object name 'Leads_Old'\r\n   at Program...",
 "@tr":"b63036a8d4861a62b736ae7f2f3912ee","@sp":"7b6bf909ae81f948","Path":"/api/leads/8842", ...}
```

`@x` chứa exception đầy đủ — thứ đã bị giấu khỏi phản hồi nhưng vẫn đến được đúng người. Thiếu bước nối này, việc giấu lỗi ở bài 1 chỉ là giấu luôn cả khỏi đội vận hành.

**Hiện mã ngắn cho người dùng.** 32 ký tự khó đọc qua điện thoại. Giao diện có thể hiện 8 ký tự đầu của trace id ("Mã tham chiếu: b63036a8"), và đội hỗ trợ tìm bằng tiền tố đó.

**Thêm ngữ cảnh nghiệp vụ.** Đẩy `TenantId`, `UserId` vào mọi dòng log của request bằng `BeginScope` hoặc `LogContext.PushProperty` trong một middleware đặt sau `UseAuthentication` ([bài 8.7](8.7-logging-with-serilog.md)), để tìm được cả "mọi lỗi của một khách hàng".

</details>

## Tự kiểm tra

<details>
<summary>Stack trace lộ ra ngoài gây rủi ro gì?</summary>

Nó tiết lộ đường dẫn trên máy build, tên lớp và phương thức nội bộ, tên thư viện; thông điệp exception đi kèm có thể chứa tên máy chủ database, tên bảng, tài khoản. Với kẻ tấn công đó là bản đồ hệ thống kèm manh mối tra cứu lỗ hổng đã biết.

</details>

<details>
<summary>Có cần gọi app.UseDeveloperExceptionPage() trong ứng dụng .NET 10 không?</summary>

Không. WebApplication tự bật trang lỗi cho lập trình viên khi môi trường là Development. Gọi nó vô điều kiện là lộ chi tiết exception ra production; cách an toàn nhất là không gọi.

</details>

<details>
<summary>Vì sao trả 403 cho tài nguyên của tenant khác là rò rỉ thông tin?</summary>

Vì kẻ tấn công so được 403 với 404 để biết id nào có thật, rồi liệt kê dữ liệu của hệ thống. Trả 404 cho cả hai trường hợp, bằng cách lọc tenant ngay trong truy vấn, thì không phân biệt được.

</details>

<details>
<summary>Vì sao switch theo kiểu exception phải đặt kiểu con trước kiểu cha?</summary>

Vì nhánh kiểu cha khớp cả kiểu con. Đặt DomainException trước NotFoundException thì nhánh NotFoundException không bao giờ chạy, và trình biên dịch báo lỗi CS8510.

</details>

<details>
<summary>Làm sao từ traceId người dùng gửi tìm ra dòng log?</summary>

traceId theo chuẩn W3C có bốn phần ngăn bởi dấu gạch ngang; phần thứ hai là trace id. Serilog ghi giá trị đó vào trường @tr của mọi dòng log trong request, nên tìm theo chuỗi đó là ra dòng log có exception đầy đủ.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **Lỗi hệ thống chỉ trả mã tra cứu**, chi tiết nằm trong log; lỗi nghiệp vụ thì nói rõ.
2. **Rò rỉ không chỉ ở thân phản hồi** — header `Server` và sự khác biệt 403/404 cũng kể chuyện về hệ thống.
3. **`traceId` nối phản hồi với log** — rẻ nhất, giá trị vận hành cao nhất.
