# 8.10 - EF Core tối thiểu: lưu dữ liệu vào database

> **Tóm tắt:** Tới bài này, dữ liệu của API vẫn nằm trong một `List` và mất sạch mỗi lần khởi động lại. Từ Module 9 trở đi, các bài và Project 2 sẽ dùng **Entity Framework Core** (EF Core) để lưu dữ liệu vào database qua một lớp `CrmDbContext`. Bài này dạy đúng phần tối thiểu để đọc hiểu và chạy được những bài đó: tạo entity và `DbContext`, đăng ký vào DI, tạo bảng bằng migration, đọc và ghi dữ liệu trong endpoint. Database dùng **SQLite**, một file trên đĩa, không cần cài server. Module 12 và 13 sẽ đi sâu: database thật, quan hệ giữa bảng, hiệu năng và concurrency.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích EF Core làm gì: ánh xạ class C# thành bảng, viết LINQ thay vì SQL tay.
- Tạo entity `Customer` và `CrmDbContext`, đăng ký `DbContext` vào DI với chuỗi kết nối lấy từ cấu hình.
- Tạo và áp dụng migration để sinh bảng từ code, thêm cột bằng migration mới.
- Viết endpoint đọc (`ToListAsync`, `FindAsync`) và ghi (`Add` rồi `SaveChangesAsync`) dữ liệu.
- Nhận ra các lỗi hay gặp: chưa chạy migration, thiếu gói, quên `SaveChangesAsync`.

**Cần biết trước:** [0.5 — Web API đầu tiên](../../stage-01-foundation/module-00-setup/0.5-first-web-api.md), [7.4 — Service lifetimes](../../stage-02-csharp-professional/module-07-dependency-injection/7.4-service-lifetimes.md), [8.6 — Configuration system](8.6-configuration-system.md).

## Nội dung bài học

### 8.10.1 — EF Core làm gì

Không có EF Core, bạn tự viết câu SQL, tự mở kết nối, tự đọc từng cột rồi gán vào object. EF Core là một **ORM** (Object-Relational Mapper) làm phần đó thay bạn:

| Phía C# | Phía database |
|---|---|
| class `Customer` | bảng `Customers` |
| property `Name` | cột `Name` |
| một object `Customer` | một dòng |
| `db.Customers.Where(c => c.Id == 5)` | `SELECT ... WHERE "Id" = 5` |
| `db.Customers.Add(c)` rồi `SaveChangesAsync()` | `INSERT INTO "Customers" ...` |

Bạn vẫn cần hiểu SQL: khi truy vấn chậm hay sai, bạn phải đọc được câu SQL mà EF Core sinh ra. Module 12 dạy phần đó.

### 8.10.2 — Cài gói và công cụ

Dùng lại project `CrmApi` ở bài 0.5, hoặc tạo mới bằng `dotnet new webapi -n CrmApi`. Trong thư mục project:

```bash
dotnet package add Microsoft.EntityFrameworkCore.Sqlite
dotnet package add Microsoft.EntityFrameworkCore.Design
dotnet tool install --global dotnet-ef
```

| Thứ cần cài | Để làm gì |
|---|---|
| `Microsoft.EntityFrameworkCore.Sqlite` | EF Core cùng **provider** cho SQLite. Đổi database là đổi gói này. |
| `Microsoft.EntityFrameworkCore.Design` | Thư viện mà lệnh `dotnet ef` cần để tạo migration. Chỉ dùng lúc phát triển. |
| Công cụ `dotnet-ef` | Lệnh `dotnet ef migrations ...`, `dotnet ef database ...`. Cài một lần cho cả máy. |

Đã cài `dotnet-ef` từ trước thì cập nhật bằng `dotnet tool update --global dotnet-ef`, để phiên bản công cụ không cũ hơn gói EF Core trong project.

### 8.10.3 — Entity và `DbContext`

Tạo thư mục `Data`, trong đó tạo hai file.

`Data/Customer.cs` là **entity**: một class bình thường, mỗi object ứng với một dòng trong bảng.

```csharp
namespace CrmApi.Data;

public class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public required string Email { get; set; }
    public DateTime CreatedAt { get; set; }
}
```

- Property tên `Id` kiểu `int` được EF Core hiểu là **khóa chính**, và database tự tăng giá trị khi thêm dòng mới. Bạn không tự tính id như bài 0.5 nữa.
- `required` bắt người tạo object phải gán `Name` và `Email`. Kiểu `string` không có `?` cũng khiến cột tương ứng là `NOT NULL`.

`Data/CrmDbContext.cs` là cửa ngõ để làm việc với database:

```csharp
using Microsoft.EntityFrameworkCore;

namespace CrmApi.Data;

public class CrmDbContext(DbContextOptions<CrmDbContext> options) : DbContext(options)
{
    public DbSet<Customer> Customers => Set<Customer>();
}
```

- Mỗi `DbSet<T>` là một bảng. Thêm entity mới thì thêm một `DbSet`.
- `(DbContextOptions<CrmDbContext> options)` ngay sau tên class là *primary constructor*: cách viết gọn của một constructor nhận `options` rồi chuyển cho lớp cha `DbContext`. `options` chứa thông tin dùng database nào, chuỗi kết nối là gì. Các thông tin này được cấu hình ở `Program.cs`, không viết cứng trong class.

### 8.10.4 — Đăng ký `DbContext` và chuỗi kết nối

Thêm chuỗi kết nối vào `appsettings.json`:

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*",
  "ConnectionStrings": {
    "Crm": "Data Source=crm.db"
  }
}
```

`Data Source=crm.db` nghĩa là database nằm trong file `crm.db` ở thư mục project.

Trong `Program.cs`, đăng ký `CrmDbContext` vào DI ngay sau `AddOpenApi()`:

```csharp
builder.Services.AddDbContext<CrmDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("Crm")));
```

`AddDbContext` đăng ký `CrmDbContext` với lifetime **Scoped**: mỗi request nhận một `CrmDbContext` riêng, dùng xong thì bị hủy (xem lại [7.4 — Service lifetimes](../../stage-02-csharp-professional/module-07-dependency-injection/7.4-service-lifetimes.md)). Vì vậy **không bao giờ** giữ một `DbContext` trong service Singleton.

`GetConnectionString("Crm")` đọc mục `ConnectionStrings:Crm` trong cấu hình, theo đúng cơ chế ở bài [8.6](8.6-configuration-system.md). Trên production, chuỗi kết nối đến từ biến môi trường hoặc kho bí mật, không nằm trong file commit lên Git.

### 8.10.5 — Migration: tạo bảng từ code

Database chưa có bảng nào. **Migration** là file C# mô tả cách đưa database từ trạng thái cũ sang trạng thái mới, do `dotnet ef` sinh ra bằng cách so sánh model hiện tại với lần migration trước.

```bash
dotnet ef migrations add InitialCreate
```

```text
Build succeeded.
Done. To undo this action, use 'ef migrations remove'
```

Lệnh này tạo thư mục `Migrations` với ba file. File quan trọng nhất là `..._InitialCreate.cs`:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(
        name: "Customers",
        columns: table => new
        {
            Id = table.Column<int>(type: "INTEGER", nullable: false)
                .Annotation("Sqlite:Autoincrement", true),
            Name = table.Column<string>(type: "TEXT", nullable: false),
            Email = table.Column<string>(type: "TEXT", nullable: false),
            CreatedAt = table.Column<DateTime>(type: "TEXT", nullable: false)
        },
        constraints: table =>
        {
            table.PrimaryKey("PK_Customers", x => x.Id);
        });
}
```

Đọc nó trước khi chạy: đúng tên bảng, đúng cột, đúng `nullable` chưa? Migration là code, và **phải được commit lên Git** cùng với thay đổi model.

Áp dụng migration vào database:

```bash
dotnet ef database update
```

File `crm.db` xuất hiện. Bên trong có bảng `Customers` và bảng `__EFMigrationsHistory`, nơi EF Core ghi lại migration nào đã chạy để lần sau không chạy lại.

File `crm.db` là dữ liệu chứ không phải code: thêm dòng `*.db` vào `.gitignore`.

### 8.10.6 — Đọc và ghi dữ liệu

Thay các endpoint dùng `List` của bài 0.5 bằng phiên bản dùng database. `Program.cs` đầy đủ:

```csharp
using CrmApi.Data;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
builder.Services.AddDbContext<CrmDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("Crm")));

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapGet("/customers", async (CrmDbContext db, CancellationToken ct) =>
    await db.Customers.AsNoTracking().OrderBy(c => c.Id).ToListAsync(ct));

app.MapGet("/customers/{id:int}", async (int id, CrmDbContext db, CancellationToken ct) =>
    await db.Customers.FindAsync([id], ct) is { } customer
        ? Results.Ok(customer)
        : Results.NotFound());

app.MapPost("/customers", async (CreateCustomerRequest request, CrmDbContext db, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(request.Name))
    {
        return Results.BadRequest("Tên khách hàng không được để trống.");
    }

    var customer = new Customer
    {
        Name = request.Name.Trim(),
        Email = request.Email,
        CreatedAt = DateTime.UtcNow,
    };
    db.Customers.Add(customer);
    await db.SaveChangesAsync(ct);

    return Results.Created($"/customers/{customer.Id}", customer);
});

app.Run();

record CreateCustomerRequest(string Name, string Email);
```

Những điểm mới so với bài 0.5:

- **`CrmDbContext db` là tham số của hàm xử lý.** ASP.NET Core lấy nó từ DI cho từng request, giống cách nó đọc `id` từ URL.
- **Mọi thao tác với database đều `async`** (`ToListAsync`, `FindAsync`, `SaveChangesAsync`) và nhận `CancellationToken ct`. Khi client hủy request, truy vấn đang chạy cũng được hủy theo. Module 6 giải thích kỹ vì sao.
- **`AsNoTracking()`** cho EF Core biết bạn chỉ đọc, không sửa, nên nó không cần theo dõi thay đổi của các object trả về. Đọc danh sách nên luôn có dòng này.
- **`Add` chưa ghi gì xuống database.** Nó chỉ đánh dấu object là "sẽ thêm". `SaveChangesAsync` mới gửi câu `INSERT`, và sau đó `customer.Id` có giá trị do database cấp.

Chạy `dotnet run`, gửi một `POST` bằng file `.http` như bài 0.5. Log của API cho thấy câu SQL mà EF Core sinh ra:

```text
INSERT INTO "Customers" ("CreatedAt", "Email", "Name")
VALUES (@p0, @p1, @p2)
RETURNING "Id";
```

Giá trị được truyền qua tham số `@p0`, `@p1`, `@p2` chứ không ghép thẳng vào chuỗi SQL. Nhờ vậy dữ liệu người dùng gửi lên không thể biến thành lệnh SQL, tức là chặn được SQL injection. Bài [12.7](../../stage-04-database-production/module-12-sql-deep-dive/12.7-stored-procedures-and-views.md) giải thích vì sao tham số hóa mới là thứ bảo vệ bạn.

### 8.10.7 — Dữ liệu còn sau khi khởi động lại, nhưng mất chữ `Z`

Tạo một khách hàng:

```text
HTTP/1.1 201 Created
Location: /customers/1

{"id":1,"name":"Nguyen Van An","email":"an@example.com","createdAt":"2026-10-17T14:11:46.750579Z"}
```

Dừng API, chạy lại, gọi `GET /customers`:

```text
[{"id":1,"name":"Nguyen Van An","email":"an@example.com","createdAt":"2026-10-17T14:11:46.750579"}]
```

Dữ liệu vẫn còn: đó là mục đích của cả bài. Nhưng để ý cuối `createdAt`: lần đầu có chữ `Z` (nghĩa là giờ UTC), sau khi đọc lại từ database thì mất.

SQLite không có kiểu ngày giờ riêng. EF Core lưu `DateTime` thành chuỗi chữ, và khi đọc lại thì không còn biết đó là giờ UTC hay giờ địa phương (`DateTimeKind.Unspecified`). Client nhận chuỗi không có `Z` có thể hiểu nhầm thành giờ Việt Nam, lệch 7 tiếng. Đây đúng là vấn đề mà bài [1.1](../../stage-01-foundation/module-01-programming-logic/1.1-variables-and-data-types.md) cảnh báo khi so sánh `DateTime` với `DateTimeOffset`. Database thật (PostgreSQL, SQL Server) có kiểu cột ngày giờ đầy đủ. Bài [13.2](../../stage-04-database-production/module-13-entity-framework-core/13.2-dbcontext-and-entity-configuration.md) chỉ cách cấu hình để giá trị đọc ra luôn được đánh dấu là UTC.

### 8.10.8 — Từ SQLite sang database thật

SQLite hợp để học và để chạy test, nhưng không dùng cho một API nhiều người truy cập cùng lúc. Đổi sang database thật chỉ cần đổi gói provider và một dòng đăng ký. Code endpoint, entity và cách viết LINQ giữ nguyên:

| Database | Gói NuGet | Dòng đăng ký |
|---|---|---|
| SQLite | `Microsoft.EntityFrameworkCore.Sqlite` | `options.UseSqlite(...)` |
| PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` | `options.UseNpgsql(...)` |
| SQL Server | `Microsoft.EntityFrameworkCore.SqlServer` | `options.UseSqlServer(...)` |

Migration thì phải tạo lại cho database mới, vì kiểu cột mỗi database một khác (`TEXT` của SQLite so với `text`, `nvarchar`...). Module 12 và 13 dùng database thật.

### 8.10.9 — Lỗi thường gặp

**`SqliteException: SQLite Error 1: 'no such table: Customers'` và API trả 500.** Database chưa có bảng: bạn quên `dotnet ef database update`, hoặc vừa xóa file `crm.db`. Chạy lại lệnh `update`.

**`Could not execute because the specified command or file was not found` khi gõ `dotnet ef`.** Chưa cài công cụ. Chạy `dotnet tool install --global dotnet-ef`, rồi mở lại terminal.

**`dotnet ef migrations add` báo lỗi khó hiểu như `Could not load file or assembly 'Microsoft.CodeAnalysis.Workspaces...'`.** Project thiếu gói `Microsoft.EntityFrameworkCore.Design`. Thông báo lỗi không nhắc tới tên gói này, nên dễ mất thời gian đoán.

**Cảnh báo `The Entity Framework tools version '10.0.2' is older than that of the runtime '10.0.13'`.** Công cụ `dotnet-ef` cũ hơn gói trong project. Phần lớn vẫn chạy được, nhưng nên `dotnet tool update --global dotnet-ef`.

**Gọi `POST` trả 201 nhưng `GET` không thấy dữ liệu mới.** Quên `await db.SaveChangesAsync(ct)`. `Add` chỉ đánh dấu, không ghi.

**Sửa entity (thêm property) rồi chạy, API báo lỗi cột không tồn tại.** Mỗi lần đổi entity phải tạo migration mới rồi `database update`. Model trong code và bảng trong database không tự đồng bộ.

**Danh sách rà soát khi thêm EF Core vào project**

- [ ] Có đủ gói provider và gói `Design`, công cụ `dotnet-ef` cùng phiên bản lớn với gói.
- [ ] Chuỗi kết nối nằm trong cấu hình, không viết cứng trong code.
- [ ] Thư mục `Migrations` được commit, file database (`*.db`) thì không.
- [ ] Truy vấn chỉ đọc có `AsNoTracking()`, mọi lời gọi database đều `async` và truyền `CancellationToken`.
- [ ] Sau `Add`, `Remove` hay sửa property đều có `SaveChangesAsync`.

## Bài tập áp dụng

#### Bài 1 — Thêm số điện thoại

Thêm property `Phone` (có thể để trống) cho `Customer` mà không làm mất dữ liệu khách hàng đang có.

**Tiêu chí hoàn thành:** migration mới chỉ thêm đúng một cột cho phép `NULL`, và khách hàng tạo trước đó vẫn còn, với `"phone": null`.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** `string?` (có dấu `?`) nghĩa là cho phép null, nên cột sinh ra sẽ cho phép `NULL`. Đặt tên migration theo việc nó làm.

**Lời giải.** Thêm vào `Customer`:

```csharp
public string? Phone { get; set; }
```

```bash
dotnet ef migrations add AddCustomerPhone
dotnet ef database update
```

Migration sinh ra chỉ có một thao tác:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(
        name: "Phone",
        table: "Customers",
        type: "TEXT",
        nullable: true);
}
```

```text
[{"id":1,"name":"Nguyen Van An","email":"an@example.com","phone":null,"createdAt":"2026-10-17T14:11:46.750579"}]
```

**Vì sao phải cho phép null?** Các dòng đã có trong bảng không có số điện thoại. Nếu khai báo `string` (không có `?`), cột sẽ là `NOT NULL` và database cần một giá trị cho các dòng cũ. Thêm cột bắt buộc vào bảng đã có dữ liệu là việc cần tính kỹ: Module 12 bàn chuyện này ở phần chiến lược migration.

</details>

#### Bài 2 — Xóa khách hàng

Viết `DELETE /customers/{id}` trả về 204 khi xóa được và 404 khi không có khách hàng đó, chỉ dùng **một** câu lệnh SQL.

**Tiêu chí hoàn thành:** log của API chỉ có một câu `DELETE`, không có câu `SELECT` nào trước đó.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Cách thông thường là `FindAsync` rồi `Remove` rồi `SaveChangesAsync`, nhưng như vậy là hai câu SQL: một `SELECT` để tải khách hàng, một `DELETE`. `ExecuteDeleteAsync` chạy thẳng câu `DELETE` trên database.

**Lời giải.**

```csharp
app.MapDelete("/customers/{id:int}", async (int id, CrmDbContext db, CancellationToken ct) =>
{
    var deleted = await db.Customers.Where(c => c.Id == id).ExecuteDeleteAsync(ct);
    return deleted > 0 ? Results.NoContent() : Results.NotFound();
});
```

Câu SQL trong log:

```text
DELETE FROM "Customers" AS "c"
WHERE "c"."Id" = @id
```

`ExecuteDeleteAsync` trả về số dòng đã xóa, nên không cần tải khách hàng trước để biết có tồn tại hay không.

**Hệ quả cần nhớ:** `ExecuteDeleteAsync` chạy **ngay lập tức**, không chờ `SaveChangesAsync`, và bỏ qua mọi thứ EF Core đang theo dõi trong bộ nhớ. Bài [13.7](../../stage-04-database-production/module-13-entity-framework-core/13.7-performance.md) bàn kỹ khi nào nên và không nên dùng nó.

</details>

## Tự kiểm tra

<details>
<summary>db.Customers.Add(customer) đã ghi dữ liệu xuống database chưa?</summary>

Chưa. `Add` chỉ đánh dấu object là sẽ được thêm. Câu `INSERT` chỉ được gửi khi gọi `SaveChangesAsync`, và sau đó `customer.Id` mới có giá trị.

</details>

<details>
<summary>Vì sao DbContext được đăng ký với lifetime Scoped?</summary>

`DbContext` theo dõi các object đã đọc và các thay đổi chưa lưu, và không an toàn khi nhiều luồng dùng cùng lúc. Mỗi request một `DbContext` riêng giúp các request không giẫm lên nhau, và mọi thứ được dọn sạch khi request kết thúc.

</details>

<details>
<summary>Migration là gì, có cần commit lên Git không?</summary>

Migration là code mô tả cách đổi cấu trúc database từ phiên bản này sang phiên bản sau. Phải commit, để máy của người khác và máy chủ production áp dụng đúng các thay đổi theo đúng thứ tự. File database (`crm.db`) thì không commit.

</details>

<details>
<summary>Khi nào thêm AsNoTracking()?</summary>

Khi truy vấn chỉ để đọc rồi trả về, không sửa object rồi lưu lại. EF Core khỏi phải theo dõi thay đổi, nên nhanh hơn và tốn ít bộ nhớ hơn.

</details>

## Kết luận

1. **EF Core ánh xạ class thành bảng và LINQ thành SQL**, nhưng bạn vẫn phải đọc được SQL nó sinh ra.
2. **Model đổi thì phải có migration.** Code và database không tự đồng bộ.
3. **`Add` chỉ đánh dấu, `SaveChangesAsync` mới ghi.**

Từ Module 9, các bài dùng `CrmDbContext` theo đúng cách trong bài này. Module 13 quay lại EF Core một cách đầy đủ: quan hệ giữa các bảng, truy vấn hiệu quả, concurrency.
