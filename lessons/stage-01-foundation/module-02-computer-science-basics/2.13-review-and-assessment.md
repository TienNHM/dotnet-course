### 2.13.2 — Luồng tổng quát của CRM

Nối các bài lại, đây là đường đi của một lần mở danh sách khách hàng trong CRM mà khoá học xây dựng:

```text
Người dùng mở trình duyệt
    -> DNS: crm.company.com -> IP của reverse proxy            (2.2)
    -> TCP + TLS tới cổng 443, proxy giữ chứng chỉ               (2.2, 2.8)
    -> GET /api/customers kèm "Authorization: Bearer <JWT>"     (2.3, 2.4)
    -> proxy chuyển tiếp HTTP tới một trong các container API   (2.8)
    -> ASP.NET Core: CORS -> xác thực JWT -> kiểm tra quyền     (2.7, 2.12)
    -> EF Core truy vấn PostgreSQL qua connection pool           (2.6)
    -> trả JSON, id kiểu long dạng chuỗi, lỗi dạng ProblemDetails (2.5)
    -> frontend hiển thị danh sách
```

Khoá học dùng **PostgreSQL** làm database mặc định, bản SQL Server có ở các bài phụ thuộc database. Hosting mặc định là container sau reverse proxy; cách triển khai lên cloud nằm ở [Module 15](../../stage-04-database-production/module-15-docker-deployment/README.md).

#### Bài 1 — Đọc JSON trong ứng dụng console (10 điểm)

Tạo project console, dán đoạn code dưới đây và chạy. Kết quả không như mong đợi. Tìm nguyên nhân và sửa.

```bash
dotnet --version          # phải bắt đầu bằng 10.0
dotnet new console -n HelloCrm
cd HelloCrm
```

```csharp
// Mô phỏng đơn giản: đọc JSON khách hàng thành đối tượng C#
using System.Text.Json;

string json = """
{
    "id": 1,
    "name": "Nguyen Van A",
    "email": "a@example.com",
    "isActive": true
}
""";

var customer = JsonSerializer.Deserialize<Customer>(json);
Console.WriteLine($"Chào mừng khách hàng: {customer?.Name} ({customer?.Email})");

record Customer(int Id, string Name, string Email, bool IsActive);
```

**Tiêu chí hoàn thành:** chương trình in ra `Chào mừng khách hàng: Nguyen Van A (a@example.com)`, và bạn giải thích được vì sao cùng JSON đó thì một API ASP.NET Core đọc đúng mà không cần sửa gì.

**Lời giải.** Chạy `dotnet run`, kết quả thật trên .NET 10:


Không có lỗi nào, chỉ có hai giá trị rỗng. `System.Text.Json` mặc định **phân biệt hoa thường**: trường `"name"` trong JSON không khớp thuộc tính `Name`, nên `Name` và `Email` không được gán. Sửa bằng bộ tuỳ chọn dành cho web:

```csharp
var customer = JsonSerializer.Deserialize<Customer>(json, JsonSerializerOptions.Web);
```

```text
Chào mừng khách hàng: Nguyen Van A (a@example.com)
```

`JsonSerializerOptions.Web` không phân biệt hoa thường và dùng tên kiểu `camelCase`. ASP.NET Core dùng sẵn bộ tuỳ chọn này cho mọi API, nên trong API bạn không gặp lỗi trên; chỉ khi tự gọi `JsonSerializer` ở chỗ khác (ứng dụng console, job nền, test) thì phải tự truyền vào.

#### Bài 2 — Lab sửa lỗi CrmLab (60 điểm)

Dùng CrmLab ở [mục 2.3.6](2.3-client.md). Qua các bài 2.3, 2.4 và 2.7 bạn đã tìm thấy vài lỗi của nó. Lab này yêu cầu **sửa** chúng và **chứng minh** đã sửa bằng `curl`.

1. **Phân quyền chức năng.** `DELETE /api/users/{id}` chỉ Admin được gọi. Tài khoản Sales gọi phải nhận `403`.
2. **IDOR.** `GET /api/customers/{id}` chỉ trả khách hàng của chính người gọi (Admin xem được tất cả). Gọi id của người khác phải nhận `404`.
3. **Tìm kiếm.** `GET /api/customers/search` không còn trả `200` kèm `success: false`. Không có kết quả thì trả `200` với mảng rỗng `[]`.
4. **Đo thời gian.** Mọi phản hồi có header `Server-Timing: app;dur=<số mili giây>`, số viết bằng dấu chấm thập phân.
5. **Viết lại luồng.** Một đoạn 5 tới 10 câu, bằng lời của bạn, mô tả đường đi của request `GET /api/customers` từ trình duyệt tới database và ngược lại, nêu tên ít nhất năm khái niệm của module.

**Mở rộng (để đạt mức Giỏi).** Endpoint tìm kiếm còn một lỗ hổng nữa, cùng loại với yêu cầu 2. Tìm nó bằng `curl` trước khi đọc lời giải, rồi sửa.

**Tiêu chí hoàn thành:** chạy được bộ lệnh kiểm chứng trong lời giải và nhận đúng các mã trạng thái ghi ở đó; đoạn văn ở yêu cầu 5 đúng thứ tự các chặng.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Yêu cầu 1 chỉ cần đổi một dòng. Yêu cầu 2 xem lại Bài 2 của [bài 2.7](2.7-authentication-and-authorization.md). Yêu cầu 4 xem lại Bài 1 của [bài 2.1](2.1-concept-learning-path.md), và nhớ thêm hai dòng `using`.

**Lời giải — các chỗ sửa trong `Program.cs`:**

```csharp
// Thêm ở đầu file
using System.Diagnostics;
using System.Globalization;
```

```csharp
// Yêu cầu 4: ngay sau var app = builder.Build();
app.Use(async (ctx, next) =>
{
    var sw = Stopwatch.StartNew();
    ctx.Response.OnStarting(() =>
    {
        ctx.Response.Headers["Server-Timing"] = string.Create(
            CultureInfo.InvariantCulture, $"app;dur={sw.Elapsed.TotalMilliseconds:F1}");
        return Task.CompletedTask;
    });
    await next();
});
```

```csharp
// Yêu cầu 2: lọc theo chủ sở hữu ngay trong điều kiện tìm
app.MapGet("/api/customers/{id:long}", (long id, ClaimsPrincipal user) =>
{
    var userId = int.Parse(user.FindFirstValue("sub")!);   // lấy từ token, KHÔNG từ request
    var customer = customers.FirstOrDefault(c =>
        c.Id == id && (c.OwnerId == userId || user.IsInRole("Admin")));
    return customer is null ? Results.NotFound() : Results.Ok(customer);
}).RequireAuthorization();
```

```csharp
// Yêu cầu 3 và phần mở rộng: trả thẳng danh sách, và chỉ tìm trong khách hàng của mình
app.MapGet("/api/customers/search", (string name, ClaimsPrincipal user) =>
{
    var userId = int.Parse(user.FindFirstValue("sub")!);
    var found = customers
        .Where(c => c.OwnerId == userId || user.IsInRole("Admin"))
        .Where(c => c.Name.Contains(name, StringComparison.OrdinalIgnoreCase))
        .ToList();
    return Results.Ok(found);   // không có kết quả thì trả mảng rỗng [], vẫn là 200
}).RequireAuthorization();
```

```csharp
// Yêu cầu 1: chỉ Admin
app.MapDelete("/api/users/{id:int}", (int id) =>
    users.RemoveAll(u => u.Id == id) > 0 ? Results.NoContent() : Results.NotFound())
   .RequireAuthorization("AdminOnly");
```

**Lỗ hổng ở phần mở rộng.** Bản gốc của endpoint tìm kiếm không lọc theo chủ sở hữu, nên An tìm `hoa` là thấy khách hàng 103 của Bình. Kết quả chạy thật trước khi sửa phần lọc:

```text
[{"id":103,"name":"Nha sach Hoa Mai","ownerId":2}] <- 200
```

**Bộ lệnh kiểm chứng.** Chạy lại CrmLab đã sửa, lấy `TOKEN` của `an@crm.local`, rồi:

```bash
B=http://localhost:5000
curl -s -i -X DELETE $B/api/users/2 -H "Authorization: Bearer $TOKEN" | head -1
for id in 101 103; do
  curl -s -o /dev/null -w "$id -> %{http_code}\n" $B/api/customers/$id -H "Authorization: Bearer $TOKEN"
done
curl -s -w " <- %{http_code}\n" "$B/api/customers/search?name=xyz" -H "Authorization: Bearer $TOKEN"
curl -s -w " <- %{http_code}\n" "$B/api/customers/search?name=hoa" -H "Authorization: Bearer $TOKEN"
curl -s -w " <- %{http_code}\n" "$B/api/customers/search?name=anh" -H "Authorization: Bearer $TOKEN"
curl -s -i $B/api/customers -H "Authorization: Bearer $TOKEN" | grep -iE "HTTP/|server-timing"
```

Kết quả chạy thật với bản đã sửa:

```text
HTTP/1.1 403 Forbidden
101 -> 200
103 -> 404
[] <- 200
[] <- 200
[{"id":101,"name":"Cong ty Anh Duong","ownerId":1}] <- 200
HTTP/1.1 200 OK
Server-Timing: app;dur=1.4
```

Số mili giây trong `Server-Timing` sẽ khác ở máy bạn; điều cần kiểm tra là có header và số dùng dấu chấm.

**Yêu cầu 5 — một đoạn mẫu:** "Trình duyệt hỏi DNS để đổi `crm.company.com` thành địa chỉ IP, rồi mở kết nối TCP và bắt tay TLS tới reverse proxy. Request `GET /api/customers` mang theo JWT trong header `Authorization`, vì HTTP không nhớ ai đã đăng nhập. Proxy chuyển request tới một thể hiện API; ở đó middleware CORS chạy trước, rồi tới xác thực token (sai thì `401`) và kiểm tra quyền (thiếu quyền thì `403`). Endpoint lấy `userId` từ token, mượn một kết nối từ connection pool và truy vấn PostgreSQL, chỉ lấy khách hàng của người đó. Kết quả trả về dạng JSON với mã `200`, kèm header `Server-Timing` để biết máy chủ mất bao lâu."

<details>
<summary><strong>Câu 2.</strong> Một nhân viên Sales đã đăng nhập gọi endpoint chỉ dành cho Admin. Mã đúng là gì? A. <code>400</code>. B. <code>401</code>. C. <code>403</code>. D. <code>404</code>.</summary>

**C.** Server đã biết người gọi là ai (đã xác thực) nhưng người đó không đủ quyền. `401` dành cho trường hợp chưa biết bạn là ai, và trả nhầm `401` khiến client cố làm mới token vô ích. Xem [bài 2.4](2.4-http-https.md) và [bài 2.7](2.7-authentication-and-authorization.md).

<details>
<summary><strong>Câu 3.</strong> Method nào được thiết kế để <em>thay thế toàn bộ</em> tài nguyên và là idempotent? A. <code>POST</code>. B. <code>PUT</code>. C. <code>PATCH</code>. D. <code>GET</code>.</summary>

**B.** `PUT` thay thế toàn bộ và idempotent: gửi lại nhiều lần cho cùng kết quả. `PATCH` sửa một phần và không bảo đảm idempotent; `POST` tạo mới và không idempotent; `GET` chỉ đọc. Xem [bài 2.4](2.4-http-https.md).

</details>

<details>
<summary><strong>Câu 4.</strong> API trả <code>{"id": 9007199254740993}</code>. Frontend JavaScript đọc được giá trị nào? A. <code>9007199254740993</code>. B. <code>9007199254740992</code>, không báo lỗi. C. Ném lỗi tràn số. D. <code>null</code>.</summary>

**B.** JavaScript lưu mọi số bằng `double`, chỉ giữ chính xác số nguyên tới 2⁵³ − 1 = 9007199254740991. Số lớn hơn bị làm tròn im lặng. Cách sửa là gửi id dạng chuỗi bằng `[JsonNumberHandling(...)]`. Xem [bài 2.5](2.5-api-and-json.md).

</details>

<details>
<summary><strong>Câu 5.</strong> Người dùng A gọi <code>GET /api/customers/103</code>, khách hàng thuộc người dùng B, và nhận dữ liệu. Endpoint đã có <code>RequireAuthorization()</code>. Đây là lỗi gì, và sau khi sửa nên trả mã nào? A. Lỗi CORS, trả <code>403</code>. B. IDOR, trả <code>403</code>. C. IDOR, trả <code>404</code>. D. Lỗi xác thực, trả <code>401</code>.</summary>

**C.** Đây là IDOR: endpoint chỉ kiểm tra đã đăng nhập, không kiểm tra quyền trên bản ghi. Trả `404` để không xác nhận bản ghi tồn tại; trả `403` giúp kẻ tấn công dò ra id hợp lệ. Xem [bài 2.7](2.7-authentication-and-authorization.md).

</details>

<details>
<summary><strong>Câu 6.</strong> Hai phiên cùng đọc số dư 1000, phiên A ghi 1500, phiên B ghi 1300, cả hai commit ở mức <code>READ COMMITTED</code>. Kết quả và cách phòng tốt nhất? A. Database báo lỗi, không cần phòng. B. Còn 1300; phòng bằng <code>UPDATE ... SET balance = balance + 300</code>. C. Còn 1800 vì database tự cộng. D. Còn 1500 vì phiên A commit trước.</summary>

**B.** Đây là lost update: cả hai giao dịch đều hợp lệ nên database không báo lỗi, và thay đổi của A biến mất. Cách rẻ nhất là cập nhật nguyên tử, tính ngay trong câu `UPDATE`; ngoài ra có `SELECT ... FOR UPDATE` hoặc khoá lạc quan bằng cột phiên bản. Xem [bài 2.6](2.6-what-is-a-database.md).

</details>

<details>
<summary><strong>Câu 7.</strong> Database chậm 30 giây. Endpoint nào nên chuyển sang không khoẻ? A. Chỉ liveness. B. Chỉ readiness. C. Cả hai. D. Không cái nào.</summary>

**B.** Readiness báo "đừng gửi request tới đây", còn liveness báo "khởi động lại tôi đi". Database chậm không phải lý do để khởi động lại tiến trình; nếu liveness cũng kiểm tra database, mọi thể hiện bị khởi động lại cùng lúc và dồn thêm tải lên database. Xem [bài 2.8](2.8-hosting-and-cloud-basics.md).

</details>

<details>
<summary><strong>Câu 8.</strong> Frontend gọi <code>GET</code> đơn giản thì chạy, nhưng <code>POST</code> với <code>Content-Type: application/json</code> báo lỗi CORS. Nguyên nhân thường gặp nhất? A. Server không hỗ trợ <code>POST</code>. B. Request JSON kích hoạt preflight <code>OPTIONS</code>, và preflight bị từ chối hoặc thiếu header CORS. C. JSON không hợp lệ. D. Trình duyệt chặn mọi <code>POST</code> sang origin khác.</summary>

**B.** `application/json` khiến request không còn là "request đơn giản", nên trình duyệt gửi preflight trước. Nếu preflight trả lỗi hoặc thiếu `Access-Control-Allow-*` (thường do `UseCors` đặt sau middleware kiểm tra quyền), request thật không được gửi. Xem [bài 2.12](2.12-quick-real-world-example.md).

</details>

<details>
<summary><strong>Câu 9.</strong> Một service tạo <code>new HttpClient()</code> cho mỗi lời gọi ra ngoài. Sau vài giờ chạy tải cao, nó bắt đầu ném <code>SocketException</code>. Vì sao? A. Do DNS hết hạn. B. Mỗi kết nối đã đóng còn nằm ở trạng thái <code>TIME_WAIT</code> một lúc, nên cổng mạng cạn dần. C. Do JSON quá lớn. D. Do GC thu gom <code>HttpClient</code> quá sớm.</summary>

**B.** Mỗi `HttpClient` mới mở kết nối mới; kết nối đóng xong chưa giải phóng cổng ngay. Tải cao thì dải cổng khả dụng cạn. Cách đúng là dùng lại `HttpClient`, trong ASP.NET Core lấy qua `IHttpClientFactory`. Xem [bài 2.2](2.2-how-the-internet-works.md).

</details>

<details>
<summary><strong>Câu 10.</strong> Hai máy API sau một load balancer. Người dùng đăng nhập xong thì một nửa số request nhận <code>401</code> với <code>"The token expired at ..."</code>, dù token vừa cấp. Nghi ngờ đầu tiên? A. Khoá ký JWT bị lộ. B. Đồng hồ một máy chạy nhanh hơn máy phát token quá 5 phút. C. CORS sai. D. Database chậm.</summary>

**B.** `exp` là mốc tuyệt đối do máy phát tính; máy kiểm tra so với đồng hồ của mình. Máy kiểm tra nhanh hơn quá `ClockSkew` (mặc định 5 phút) thì token vừa cấp đã "hết hạn". Lỗi chỉ xảy ra một nửa số lần vì chỉ một máy lệch. Xem [bài 2.11](2.11-mini-case-study.md).

</details>

## Kết luận

Ba điều đáng nhớ nhất của Module 2:

1. **Mỗi tầng có quy tắc riêng, và lỗi thường nằm ở chỗ giao nhau**: header không ASCII, số lớn qua JSON, đồng hồ giữa hai máy, thứ tự middleware.
2. **Bảo mật nằm ở server.** Giao diện ẩn nút, CORS, hay việc đã đăng nhập đều không thay được kiểm tra quyền trên từng bản ghi.
3. **Chẩn đoán bằng đo đạc, không bằng đoán.** `curl -i`, DevTools, `Server-Timing` và thông điệp lỗi trong header nói cho bạn biết chặng nào hỏng.
