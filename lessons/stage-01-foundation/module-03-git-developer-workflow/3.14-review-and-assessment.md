## Phần A — Quiz (30 điểm, mỗi câu 3 điểm)

Ghi đáp án và một dòng lý do cho từng câu **trước khi** mở phần giải thích.

**Câu 1.** Bạn vừa `git commit --amend -m "fix: correct typo"` cho commit cuối (chưa push). Phát biểu nào đúng?

A. Git sửa message của commit cũ, mã băm giữ nguyên.
B. Git tạo commit mới với mã băm mới; commit cũ vẫn còn trong kho và tìm lại được qua `git reflog`.
C. Commit cũ bị xoá vĩnh viễn ngay lập tức.
D. `--amend` chỉ sửa message, không bao giờ đưa thêm file vào commit.

<details>
<summary>Đáp án câu 1</summary>

**B.** Commit là bất biến; mã băm tính từ nội dung, kể cả message ([bài 3.1](3.1-git-intro-and-motivation.md)). D sai vì `--amend` gộp luôn mọi thứ đang nằm trong staging vào commit mới.

</details>

**Câu 2.** Sau `git fetch`, `git status` báo `Your branch is behind 'origin/main' by 2 commits`. File trong thư mục làm việc của bạn đã đổi chưa?

A. Rồi, `fetch` đã cập nhật file.
B. Chưa. `fetch` chỉ cập nhật `origin/main`; phải `git pull` (hoặc merge/rebase `origin/main`) thì nhánh và file mới đổi.
C. Chưa, vì `fetch` không tải gì về, chỉ so sánh.
D. Rồi, nhưng chỉ với file chưa sửa.

<details>
<summary>Đáp án câu 2</summary>

**B.** `origin/main` là bản ghi nhớ trên máy về vị trí nhánh trên remote ([bài 3.4](3.4-basic-git-workflow.md)). C sai vì `fetch` có tải commit về, chỉ không gộp vào nhánh của bạn.

</details>

**Câu 3.** Bạn thêm `appsettings.Production.json` vào `.gitignore`, nhưng `git status` vẫn báo file đó đã sửa. Vì sao, và làm gì?

A. `.gitignore` sai cú pháp; thêm dấu `/` ở đầu.
B. File đã được theo dõi từ trước; `.gitignore` không hồi tố. Chạy `git rm --cached appsettings.Production.json` rồi commit — và nếu file có bí mật đã push thì thu hồi bí mật trước.
C. Phải chạy `git clean -fd`.
D. Phải xoá thư mục `.git` và `git init` lại.

<details>
<summary>Đáp án câu 3</summary>

**B** ([bài 3.2](3.2-git-install-config.md)). C xoá file chưa theo dõi, không liên quan và có thể làm mất file. D xoá toàn bộ lịch sử.

</details>

**Câu 4.** Bạn sửa dở ba file và tạo thêm một file mới, chưa commit. Có lỗi gấp phải sang nhánh khác sửa ngay. Lệnh nào cất **hết** việc dở?

A. `git stash`
B. `git stash -u`
C. `git reset --hard`
D. `git clean -fd`

<details>
<summary>Đáp án câu 4</summary>

**B.** `stash` mặc định không cất file chưa theo dõi; `-u` cất cả chúng ([bài 3.3](3.3-git-safety-checklist.md)). C và D xoá mất việc dở, không cứu lại được.

</details>

**Câu 5.** Bạn lỡ `git reset --hard HEAD~3` trên nhánh chưa push. Ba commit đó còn cứu được không, và bằng cách nào?

A. Không, `--hard` xoá vĩnh viễn.
B. Có: `git reflog` tìm mã commit trước khi reset, rồi `git reset --hard <mã>` (hoặc `git branch rescue <mã>`), trong khoảng 30 ngày theo mặc định.
C. Có, nhưng chỉ khi đã push.
D. Có: `git revert HEAD~3`.

<details>
<summary>Đáp án câu 5</summary>

**B** ([bài 3.3](3.3-git-safety-checklist.md)). Thứ `--hard` xoá vĩnh viễn là **thay đổi chưa commit**, không phải commit.

</details>

**Câu 6.** Đang ở nhánh `feature/report`, bạn chạy `git rebase main` và gặp xung đột. Bạn gõ `git restore --ours Report.cs` với ý "giữ code của tôi". Chuyện gì xảy ra?

A. Giữ code của bạn, đúng ý.
B. Giữ phiên bản của `main`: trong rebase, "ours" là nhánh đích, còn commit của bạn là "theirs".
C. Git báo lỗi vì không dùng được `--ours` khi rebase.
D. Giữ cả hai bên.

<details>
<summary>Đáp án câu 6</summary>

**B** ([bài 3.7](3.7-git-conflicts.md)). Khi rebase, Git đứng trên nhánh đích và phát lại từng commit của bạn lên trên, nên "ours" là `main`. Cách an toàn: mở file ra đọc dấu xung đột.

</details>

**Câu 7.** Bạn rebase nhánh cá nhân đã push lên GitHub và cần đẩy lại. Lệnh nào phù hợp nhất?

A. `git push --force`
B. `git push --force-with-lease --force-if-includes`
C. `git pull` rồi `git push`
D. `git push --no-verify`

<details>
<summary>Đáp án câu 7</summary>

**B** ([bài 3.3](3.3-git-safety-checklist.md)). `--force-with-lease` từ chối nếu remote có commit bạn chưa thấy; `--force-if-includes` vá trường hợp bạn vừa `fetch` ngay trước đó. C trộn lại lịch sử cũ với lịch sử đã rebase, tạo commit trùng lặp.

</details>

**Câu 8.** PR của bạn được **squash merge** trên GitHub. Về máy, `git branch -d feature/report` báo `not fully merged`. Vì sao?

A. PR chưa thật sự được merge.
B. Squash merge tạo một commit **mới** trên `main`; các commit gốc của nhánh không nằm trong `main`, nên Git không biết nhánh đã được gộp. Xác nhận PR đã merged rồi xoá bằng `-D`.
C. Phải `git fetch` trước thì `-d` mới chạy.
D. Nhánh đang bị khoá bởi branch protection.

<details>
<summary>Đáp án câu 8</summary>

**B** ([bài 3.5](3.5-branching-and-merging.md), [bài 3.8](3.8-real-world-developer-workflow.md)).

</details>

**Câu 9.** Nhánh A đổi tên `CalculateRevenue` thành `CalculateAnnualRevenue`; nhánh B (tách cùng lúc) thêm một file mới gọi `CalculateRevenue`. Merge cả hai vào `main`. Điều gì xảy ra?

A. Git báo xung đột ở file mới.
B. Git merge sạch, nhưng `dotnet build` báo lỗi CS1061. Chỉ CI chạy build/test trên kết quả merge mới bắt được.
C. Git tự sửa chỗ gọi theo tên mới.
D. Cả hai merge đều bị từ chối.

<details>
<summary>Đáp án câu 9</summary>

**B** — xung đột ngữ nghĩa ([bài 3.7](3.7-git-conflicts.md)). Git làm việc trên dòng văn bản, không hiểu C#.

</details>

**Câu 10.** Một bạn lỡ push mật khẩu database production lên kho công khai 5 phút trước. Việc **đầu tiên** phải làm là gì?

A. `git rm --cached` file đó và push.
B. Chạy `git filter-repo` xoá file khỏi lịch sử.
C. Đổi mật khẩu database và ngắt các phiên đang mở; dọn lịch sử làm sau.
D. Chuyển kho sang riêng tư.

<details>
<summary>Đáp án câu 10</summary>

**C** ([bài 3.12](3.12-mini-case-study.md)). A và B không thu hồi được các bản sao đã bị clone hay bị bot đọc; D cũng vậy. Đổi mật khẩu không tự ngắt phiên cũ, nên phải ngắt chúng.

</details>

## Phần B — Lab (70 điểm)

Làm trên máy của bạn, trong **một** kho tên `crm-git-review`. Mỗi lab có tiêu chí kiểm tra được; nộp đường dẫn kho GitHub và file `LAB.md` ở gốc kho ghi output các lệnh được yêu cầu.

### Lab 1 — Kho đầu tiên lên GitHub (15 điểm)

1. Tạo kho trên máy với nhánh đầu tiên là `main` (dùng `git init -b main`, vì trên nhiều máy Windows giá trị mặc định vẫn là `master`).
2. Tạo project bằng `dotnet new console -n Crm -o .`, thêm `.gitignore` bằng `dotnet new gitignore`, thêm `.gitattributes` có dòng `* text=auto`.
3. Commit theo Conventional Commits.
4. Trên GitHub, tạo kho **trống** `crm-git-review` (không tick *Add a README*), rồi `git remote add origin ...` và `git push -u origin main`.

**Tiêu chí kiểm tra:** trang GitHub của kho hiện `Program.cs`, `Crm.csproj`, `.gitignore`, `.gitattributes`, **không** có thư mục `bin/` hay `obj/`; `git branch -vv` (ghi vào `LAB.md`) cho thấy `main` theo dõi `origin/main`.

<details>
<summary><strong>Lời giải — Lab 1</strong></summary>

```bash
mkdir crm-git-review && cd crm-git-review
git init -b main
dotnet new console -n Crm -o .
dotnet new gitignore
echo "* text=auto" > .gitattributes
git add .
git status                 # kiểm tra: không có bin/ hay obj/
git commit -m "chore: initialize CRM console project"
git remote add origin https://github.com/<ten-ban>/crm-git-review.git
git push -u origin main
git branch -vv
```

Nếu gặp `error: src refspec main does not match any`: hoặc chưa commit, hoặc nhánh đang tên `master` — đổi bằng `git branch -M main`.

</details>

### Lab 2 — Nhánh, pull request, squash merge (20 điểm)

1. Tạo nhánh `feature/customer-notes` từ `main`.
2. Tạo file `docs/customer-notes.md` mô tả tính năng "ghi chú cho khách hàng" (vài dòng là đủ, không cần viết code), commit. Sửa thêm một ý, commit lần hai. Cả hai message theo Conventional Commits.
3. Push nhánh, mở pull request với mô tả theo cấu trúc ở [bài 3.6](3.6-github-and-pull-request.md): *Vì sao*, *Làm gì*, *Cách kiểm tra*, *Lưu ý cho người review*.
4. Squash merge PR (tiêu đề PR theo Conventional Commits), rồi dọn nhánh ở cả GitHub và máy.

**Tiêu chí kiểm tra:** trên `main` có **một** commit mới cho PR, message bắt đầu bằng `feat:` hoặc `docs:`; PR có đủ bốn mục mô tả; `git branch` trên máy không còn `feature/customer-notes`; `LAB.md` ghi lại lệnh đã dùng để xoá nhánh và giải thích vì sao dùng `-D`.

<details>
<summary><strong>Lời giải — Lab 2</strong></summary>

```bash
git switch -c feature/customer-notes
mkdir docs
printf '# Ghi chú khách hàng\n\nNhân viên thêm ghi chú cho mỗi khách hàng.\n' > docs/customer-notes.md
git add docs && git commit -m "docs: describe customer notes feature"
printf 'Mỗi ghi chú lưu người viết và thời điểm.\n' >> docs/customer-notes.md
git commit -am "docs: add author and timestamp to customer notes"
git push -u origin feature/customer-notes
# Mở PR trên GitHub (đường dẫn in ra sau lệnh push), viết mô tả, chọn "Squash and merge"
git switch main
git pull
git branch -D feature/customer-notes    # -d sẽ báo "not fully merged" sau squash merge
git fetch --prune
git log --oneline -3
```

PR có hai commit nên GitHub mặc định đề xuất **tiêu đề PR** làm dòng đầu của commit squash ([bài 3.10](3.10-conventional-commits.md)) — vì vậy tiêu đề PR phải theo quy ước.

</details>

### Lab 3 — Giải xung đột (20 điểm)

Trong cùng kho, chạy đoạn sau (Git Bash, macOS hoặc Linux). Đây là **một** kho, hai nhánh tách từ cùng một commit; không cần hai terminal.

```bash
git switch main
printf '# Quy tắc cập nhật khách hàng\n1. Tên không được rỗng.\n2. (chưa có quy tắc liên hệ)\n' > customer-rules.md
git add customer-rules.md && git commit -m "docs: add customer update rules"

git switch -c feature/email-validation
printf '# Quy tắc cập nhật khách hàng\n1. Tên không được rỗng.\n2. Email phải có dạng ten@mien.\n' > customer-rules.md
git commit -am "docs: require a valid email when updating a customer"

git switch main
git switch -c feature/phone-validation
printf '# Quy tắc cập nhật khách hàng\n1. Tên không được rỗng.\n2. Số điện thoại phải có 10 chữ số.\n' > customer-rules.md
git commit -am "docs: require a 10-digit phone number when updating a customer"

git switch main
git merge feature/email-validation
git merge feature/phone-validation      # xung đột
```

Giải xung đột sao cho **giữ cả hai quy tắc** (email là quy tắc 2, số điện thoại là quy tắc 3), hoàn tất merge và push `main`.

**Tiêu chí kiểm tra:** `customer-rules.md` trên `main` có đúng ba quy tắc, không còn dòng nào chứa `<<<<<<<`, `=======` hay `>>>>>>>`; `git log --oneline --graph` (dán vào `LAB.md`) có một merge commit với hai cha.

<details>
<summary><strong>Lời giải — Lab 3</strong></summary>

Output thật của lệnh merge thứ hai:

```text
Auto-merging customer-rules.md
CONFLICT (content): Merge conflict in customer-rules.md
Automatic merge failed; fix conflicts and then commit the result.
```

```text
# Quy tắc cập nhật khách hàng
1. Tên không được rỗng.
<<<<<<< HEAD
2. Email phải có dạng ten@mien.
=======
2. Số điện thoại phải có 10 chữ số.
>>>>>>> feature/phone-validation
```

Sửa file thành (bằng tay hoặc **Accept Both Changes** trong VS Code rồi đánh lại số):

```text
# Quy tắc cập nhật khách hàng
1. Tên không được rỗng.
2. Email phải có dạng ten@mien.
3. Số điện thoại phải có 10 chữ số.
```

```bash
git add customer-rules.md
git commit --no-edit
git log --oneline --graph -5
git push
```

```text
*   413c0ed Merge branch 'feature/phone-validation'
|\
| * 2c2962f docs: require a 10-digit phone number when updating a customer
* | 77a7987 docs: require a valid email when updating a customer
|/
* a0aba22 docs: add customer update rules
```

Merge đầu tiên là fast-forward (`main` chưa có commit mới), nên chỉ merge thứ hai mới tạo merge commit. Mã băm trên máy bạn sẽ khác.

</details>

### Lab 4 — Cứu dữ liệu (15 điểm)

1. Tạo nhánh `practice/rescue`, tạo 3 commit nhỏ trên đó. Ghi `git log --oneline -4` vào `LAB.md`.
2. Chạy `git reset --hard HEAD~2`. Dùng `git reflog` khôi phục nhánh về đúng commit cuối.
3. Sửa `customer-rules.md` (file đã có từ Lab 3) và tạo một file mới `todo.md`, **không commit**. Cất cả hai bằng một lệnh, chuyển sang `main`, quay lại `practice/rescue` và lấy lại.

**Tiêu chí kiểm tra:** sau bước 2, `git log --oneline -4` giống hệt bước 1 (cùng mã băm); sau bước 3, `git status --short` hiện lại ` M customer-rules.md` và `?? todo.md`. `LAB.md` có output của `git reflog` dùng ở bước 2.

<details>
<summary><strong>Lời giải — Lab 4</strong></summary>

```bash
git switch -c practice/rescue
for i in 1 2 3; do echo "bước $i" >> rescue.txt; git add rescue.txt; git commit -m "chore: rescue practice step $i"; done
git log --oneline -4

git reset --hard HEAD~2
git reflog -4
# dòng "commit: chore: rescue practice step 3" cho biết mã cần lấy lại
git reset --hard <mã đó>
git log --oneline -4          # giống hệt lần đầu

echo "sửa dở" >> customer-rules.md
echo "- việc cần làm" > todo.md
git stash push -u -m "wip: rescue practice"
git switch main
git switch practice/rescue
git stash pop
git status --short
```

Quên `-u` thì `todo.md` không được cất và vẫn nằm trong thư mục khi bạn chuyển sang `main` — đó là cái bẫy mà lab này muốn bạn nhìn thấy.

</details>
